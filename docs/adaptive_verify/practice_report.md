# DSpark 自适应校验在 Ascend NPU 上的工程实践

## 摘要

本文总结 DSpark 自适应校验（adaptive verification，下称 AV）在 Ascend NPU 上从变
长算子契约、整网等价、入图到收益验证的工程实践。

开发这类能力要同时处理五个问题：如何让一条按固定草稿宽度设计的投机解码路径接受逐
请求不同的校验宽度；如何让被裁剪过的批次仍然命中已捕获的图，而不是掉回 eager；如
何在有状态算子上保证 shape 变化不改变状态读写契约；如何在「裁剪省下单步时间」与
「裁剪压低接受率」互相抵消时证明净收益；以及如何在参考实现自身不可复现时仍然给出
可用的正确性判据。

本实践依次解决这些问题：先用独立 CPU golden 固定变长算子的数学契约，再在 eager
下跑通整网逐 token 等价并建立「必须真的裁过」的活性门禁；随后按参考设计的六个
batch size 契约进入 ragged 全图，把 GDN 请求轴钉死以换取所有 bucket 共用一套状态
契约；最后用进程级噪声底做冻结版本的收益对比——而当逐 token 判据在最后一步被证明
不成立时，把判据本身当成被测对象重新定义。

最终，在 Qwen3.6-27B、TP=4、`max_num_seqs=16`、Dolly 数据集、输出定长 256 token
的冻结对比中：固定 K 基线吞吐 441.3 toks/s，开启 AV 后 457.3 toks/s，**+3.6%**，
同期进程级噪声底为 **0.6%**；平均接受长度由 3.33 降至 3.22；单请求解码时延 p99
由 12.89 ms 微降至 12.84 ms。变长算子对独立 CPU golden 的门禁 5/5 通过，CPU 单元
测试 49 个测试函数（77 个用例）全绿。

**关键词**：Ascend NPU、vLLM、投机解码、自适应校验、ACL Graph 全图回放、Gated
Delta Net、变长算子、cost table

## 1 实践简介

### 1.1 业务背景

诉求链条很短：客户要 Qwen3.6-27B 在 Ascend NPU 上的解码吞吐 → 吞吐提升依赖投机解
码的接受率与单步成本 → DSpark 的草稿宽度 K 由 checkpoint 固定（`speculative.py:177`
要求 `num_speculative_tokens == block_size`，不可调）→ 唯一剩下的空间是**逐请求
地少校验一些注定被拒的草稿**。

这就是上游 AV 的设计：草稿模型在产出草稿的同一次前向里额外输出一个 confidence
head，controller 用它估计每个草稿位置的存活概率，再按 cost table 做 argmax，给每
个请求一个本轮的校验预算。被裁掉的草稿不进校验批次，于是校验批次变短、单步变便宜；
代价是接受长度下降。

Ascend 侧的问题不在策略，在**几何**：裁剪让每个请求的 query 长度不再相等，而这条
路径上的算子、图描述符和状态契约全都是按「每请求 K+1 个 token」设计的。

### 1.2 方法概览

**图 1 从算子契约到收益验证的四阶段路线，以及每阶段的通过门禁。**

路线是 eager → PIECEWISE → ragged FULL，不是 eager → FULL。两条理由：

**归因理由**：直接进 FULL 会让「算子算错」和「图回放错」混在一起。PIECEWISE 提供
一条能长期对照的正确性基线。

**更硬的理由是 cost table。** 参考设计在同一类模型上实测（Qwen3.3-9B，TP=2，
target 侧单步成本）：

| capture_size | eager (ms) | PIECEWISE (ms) |
| --- | --- | --- |
| 16 | 84.25 | 33.88 |
| 64 | 80.18 | 39.76 |
| 256 | 79.31 | 43.98 |
| 512 | 79.88 | 59.06 |

**eager 下成本在 76–84 ms 之间几乎水平**——Q 从 16 到 512 没有可区分的代价差异。
这意味着在 eager 下 controller 选哪个 Q 单步时间都一样，**裁剪决策在性能上毫无意
义**。图外固定开销（算子启动、TP 通信、边界同步）在 eager 中占主导；PIECEWISE 把
它压下来之后曲线才开始随 Q 单调；ragged FULL 进一步拉开到 25.87 → 103.09 ms。

**图 3 eager 下成本曲线是水平的，所以裁剪在 eager 下不可能换来时间；只有进入图模
式后曲线才随 Q 单调。**

由此得到一条贯穿全程的纪律：**在图模式之前不要用真实 cost table 替换合成曲线，也
不要谈收益。** 本实践的 eager 阶段结论只能是「布局正确」，不能是「有收益」。

选择 Decode 侧先行、Prefill 后置的理由同样是归因：decode 批次的几何稳定（每请求
K+1），先在这里固定契约，再处理混合批。

### 1.3 关键结果

- **组件级**：ragged 全图下的真实 cost table 在服务可达范围内有梯度——
  `max_num_seqs=16`、graph_limit=128 时 Q=1 为 29.05 ms、Q=128 为 59.25 ms，可达
  区间跨度 30.20 ms。这是「裁剪能换到更便宜的 bucket」的直接证据。
- **端到端**：457.3 对 441.3 toks/s，+3.6%，噪声底 0.6%。接受长度 3.33 → 3.22（按
  设计下降），p99 单请求解码时延未恶化。
- **接入验证**：aggregated warn 行同时出现 `graph=FULL` 与 `kept<100%`，证明被裁
  剪的批次确实在回放全图而不是掉回 eager。
- **正确性**：变长算子对独立 FP64 NumPy golden 5/5 通过，含多轮状态续接；CPU 单
  测 49 个函数全绿。
- **边界**：逐 token 等价判据在 `max_num_seqs=16`、256 token 规模下**不成立**——
  参考自身 8 次采样产出 4 种不同输出，最早分歧在 token 2。这一条写在第 5.4 和第
  7 节。

## 2 痛点与挑战

### 2.1 量化痛点：白算的 token 比产出的还多

K=7 固定宽度意味着每个请求每步送入校验的是 8 个 token（7 个草稿 + 1 个 bonus）。
实测平均接受长度 3.33。于是：

```
单请求单步校验 token = K + 1 = 8
单请求单步被接受   = 3.33
单请求单步被拒     = 8 − 3.33 = 4.67
```

放到一次完整的基准负载（500 请求 × 输出 256 token，`max_num_seqs=16`，实测占用
15.6）：

```
总解码步数 ≈ 500 × 256 / (15.6 × 3.33) ≈ 2 466 步
总校验 token ≈ 2 466 × 15.6 × 8    ≈ 307 700
其中被接受                           = 128 000
其中被拒（白算）                     ≈ 179 700  → 占全部校验 token 的 58%
```

**白算的 token 比最终产出的 token 还多约 40%。** 这个式子有三个用处：它证明浪费
会被步数放大（所以值得做）；它给出后面接入验证的期望量级（aggregated 行里必须出
现 `kept` 低于 100% 的窗口）；它让读者能用自己的接受率重算。

但同一组数据也给出了**收益上限**，这一点必须和痛点一起给，否则后面的 +3.6% 会显
得过小。从 TPS 与接受长度反推单步时间：

```
steps/s = TPS / (占用 × 接受长度)
基线：441.3 / (15.6 × 3.33) = 8.50 步/s → 117.7 ms/步
AV  ：457.3 / (15.6 × 3.22) = 9.10 步/s → 109.8 ms/步
```

而 cost table 说 Q=128 时 target 前向为 59.25 ms，其中只有 30.20 ms 随校验 token
数变化（实测表见第 5.2 节）。**也就是说：58% 的 token 被白算，但只有约 26% 的单
步时间随这些 token 的数量变化**（30.20 / 117.7）。剩下的部分是前向的固定成本、草
稿链、拒绝采样、状态更新、调度与通信——AV 碰不到。

### 2.2 为什么朴素方案不行

**朴素方案一：把 K 调小。** K 由 checkpoint 固定，不可调；即便可调，全局调小对高
接受率的请求是净损失。浪费是逐请求的，解法也必须是逐请求的。

**朴素方案二：裁剪之后让批次掉回 eager。** 这是实现上最省事的做法，也是第 1.2 节
那张表否掉的做法——eager 下 Q 对单步成本没有可区分影响，裁剪不产生任何时间差异。**「
能裁」不等于「有收益」，收益的前提是图。**

**朴素方案三：让裁剪后的批次掉回 PIECEWISE。** 技术上可行且正确，但要多编译一整
套图，显存压力不可接受。更关键的是口径问题：**AV 关闭时混合批同样走 eager，若只
让 AV 享有 piecewise，测出来的收益里混进了一个配置选择。** 本实践据此把
`VLLM_ASCEND_DSPARK_AV_KEEP_PIECEWISE` 默认置 0，并让「拒绝入图」的批次落到配置
本身给的去处（`FULL_DECODE_ONLY` 下即 eager）。

**朴素方案四：把融合范围做到最大，让 ragged 全图也吃混合批。** 参考设计明确把这
条列为未来工作：ragged FULL 的契约是纯投机解码，混合批应当离开它。强行合并会扩大
ABI 与 fallback 范围，**并且让性能变化无法归因**——这是技术权衡升级为方法论权衡的
地方。

### 2.3 核心挑战

四条挑战有一个共同特征：**错误不会立即暴露。** 这直接解释了第 3 章为什么需要那么
多门禁。

**挑战 1：固定宽度契约渗透进有状态算子。** GDN（Gated Delta Net）是循环状态算子。
对无状态算子，缩小 shape 往往只是性能问题；**对有状态算子，shape 变化还会改变
状态读写契约。** 早期让 GDN 请求轴跟随图尺寸（Q=32 用 32 行、Q=64 用 64 行），单
机稳定并发下正常，PD 分离联调时才暴露：并发由小到大爬升时不同图的 stateful
tiling 与请求轴反复变化，前面几批请求短输出或乱码，并发稳定后恢复正常。**不报错，
而且会自愈。**

**挑战 2：图回放的兼容判据过宽。** `_is_compatible` 接受任何「请求数 ≤、token 数
≤、max_query_len ≤」的批次。这正是裁剪后的批次能回放变长 decode 图的原因，也意味
着含真实 prefill 的混合批会在 prefill 比 decode 窄时漏进 decode 图。同一个宽松判
据既是功能的前提，又是错误的入口。

**挑战 3：置信度信号可能静默冻结。** 出图后 confidence 算子只有被 trace 进捕获的
草稿图才会每次回放都重算；一个在 capture 时为假的 Python 分支会把它整个留在图外，
于是 buffer 冻在 capture 前的值，每个预算都基于停止更新的数字。而**输出逐
token 不变**——裁剪只是策略，拒绝采样仍然正确，token 与固定 K 跑出来完全一致。唯
一症状是「AV 看起来没效果」，可以藏几周。任何输出对比都抓不到它。

**挑战 4：正确性判据本身可能不成立。** 本实践最后发现：TP=4 下，去掉 AV 的参考实
现自己就不可复现。逐 token 相等作为正确性工具在这个配置下失效。这条挑战在开工时
没有被预见到，它是第 5.4 节和第 7 节的主要内容。

挑战与方法一一对应：挑战 1 对应 W3 的 `B_gdn = B_max` 与零长度 padding 行；挑战
2 对应 W3 的混合批拒绝；挑战 3 对应 W1 的 `conf_moved` 活性门禁；挑战 4 对应 W4
的噪声底与参考集判据。

## 3 方法

### 3.1 阶段划分与门禁

| 阶段 | 目标 | 关键动作 | 进入条件 | 通过条件 |
| --- | --- | --- | --- | --- |
| **W0** 算子契约 | 变长卷积与变长循环在数学上正确 | 写独立 FP64 NumPy 参考；对装好的算子逐点比对；多轮状态续接 | 有可用的变长算子 API | 独立 golden 全通过，含零长度行与「accepted 大于本轮宽度」用例；状态按位比对 |
| **W1** eager 整网等价 | 裁剪不改变输出，且确实裁过 | 整网跑门槛脚本，三条 lane 对固定 K 基线逐 token 比对 | W0 通过 | 输出等价 **且** aggregated 行显示 `kept<100%` **且** `conf_moved≈N/N` |
| **W2** cost table 可用 | 确认裁剪在本规模下能换到更便宜的 bucket | 启动时 profile 真实 cost table，打印可达 Q 区间的跨度与判决 | W1 通过，且已进入某种图模式 | 可达区间跨度超过代码内的平坦容差 `_FLAT_COST_TOLERANCE_MS`（本实践实测 30.20 ms）；若判为平，正确结论是「不裁」而非继续优化 |
| **W3** ragged 全图 | 裁剪后的批次回放已捕获的图 | 六个 batch size 契约；`B_gdn = B_max`；FIA padding 行；混合批拒绝 | W2 显示有梯度 | 整网不崩 **且** `graph=FULL` 与 `kept<100%` 同时出现 **且** 宽请求轴被真实行使（存在 padding 行） |
| **W4** 收益对比 | 给出可审计的净收益 | 冻结版本；进程级噪声底；定长输出；占用与接受率同时记录 | W3 通过 | 收益至少为噪声底的 3 倍（本实践 3.6% 对 0.6%，6 倍）；接受率下降与单步改善能对账；p99 时延未恶化 |

两列条件是这张表的全部价值。「通过条件」都写成可判定的：不是「性能达到预期」，而
是「`graph=FULL` 与 `kept<100%` 在同一窗口同时出现」。

### 3.2 阶段之间不是机械的先后工序

**W0 和 W1 是每个项目都要做的入口。W2 是分流点，W3 是条件触发的。**

W2 的判决如果是「可达 Q 区间内曲线平坦」，正确的做法是**停下来，并把「不裁剪」记
为正确决策**——此时无论 confidence 多准，controller 都没有可优化的目标。本实践的
`_report_cost_table` 直接把这句判决打进日志，就是为了让后来者不必靠猜：

```text
flat: trimming cannot pay at this scale, and declining to trim is the correct decision
```

进入 W3 需要同时满足：

1. W2 显示可达区间有梯度；
2. 混合批有明确去处（本实践的去处是 eager，与 AV 关闭时一致）；
3. 有状态算子的请求轴可以被钉死（否则 shape 变化会改变状态契约）；
4. 有一条能长期对照的正确性基线（PIECEWISE 或 eager）。

参考设计把 PIECEWISE 作为中间站，本实践**最终排除了它**——不是因为它不正确，而是
因为多编一套图的显存代价不可接受，且它会污染收益口径（第 2.2 节）。这是一处对参
考设计的主动偏离，理由写在这里，不藏。

### 3.3 每一步的输入、产物与门禁

| 阶段 | 主要输入 | 产物 | 门禁 |

## 4 实践过程

### 4.1 W0：变长算子的数学契约

#### 4.1.1 合同

这一阶段固定下来的，是**两个轴的解耦**：

| 轴 | 是否随本轮 query 变化 |
| --- | --- |
| 本轮每请求的 query 长度（`query_start_loc` 的差分） | **变**，可逐请求不同，可为 0 |
| 状态表的 stride `S = K+1` | 不变 |
| `num_accepted_tokens`（上一轮产出数，用作历史选择器） | 不变，且**允许大于本轮宽度** |

循环算子的契约：状态从 `indices[row, accepted-1]` 读，候选 t 写
`indices[row, t]`。卷积的契约：每个活跃行从物理 slot 的 `accepted-1` 处读 3 个历
史样本，把 `history[-2:] + 本轮 x` 写到 **offset 0**，其余 state 不动——正因为写
布局固定在 offset 0，下一轮才能选任意 accepted 前缀，与下一轮的 query 长度无关。

零长度行必须被跳过：`cache_indices[row] = PAD_SLOT_ID`（-1），算子不得读写该行的
state。

#### 4.1.2 做法

新增一对算子，与原有的固定 K 算子并存，由 `use_eager_varlen` 分流：

| | 固定 K 路径（原有） | D-Cut 变长路径（新增） |
| --- | --- | --- |
| 卷积 | `npu_causal_conv1d_custom` | `npu_dcut_causal_conv1d` |
| 循环 | `npu_recurrent_gated_delta_rule` | `npu_dcut_recurrent_gated_delta_rule` |
| 长度入参 | `actual_seq_lengths` | `query_start_loc`（cumsum） |
| 状态索引传法 | `.flatten()` | `.contiguous()`，**保留 `[B, S]` 二维** |

`.flatten()` 是关键差异。扁平化之后寻址只能按固定 stride `K+1` 隐式推算，**每个
请求必须恰好 K+1 个 token**；保留二维才能让每行用掉的列数不同。

**收益来自状态索引保持二维，而不是多传了一个偏移表。** 偏移表只描述 query 轴；真
正让「每行用几列」可变的是状态表不被压平。

#### 4.1.3 实验台账

| 实验 | 主要变量 | 结果 | 决策 | 说明 |
| --- | --- | --- | --- | --- |
| 接入变长卷积 | 把投机路径从固定 K 卷积切到变长卷积 | `[8]`、`[3,1,4]`、`[1,1,1]` 通过，`[8,0,0,0,0,0,0,0]` 失败 | 继续补证据 | 失败形态见下 |
| 让偏移表决定 layout | host tiling 的 `inputMode` 推断改为以 `query_start_loc` 为准（opt-in，仅新算子） | 设备上**无变化** | 回退判定为「修复无效」，继续定位 | 见下 |
| 给 tiling 单元私有命名空间 | 把共享 host helper 的命名空间在新算子的编译单元里改名 | `[8,0,…]` 通过，5/5 全绿 | 接受 | 第一步此前被链接器丢掉 |
| ArgSort 键类型 | 把 bool/int 排序键转 float32 | 消除 AiCPU 回退告警 | 接受 | ArgSort 无 int32/int64 的 AiCore 实现 |

表中每个结果对应当时的实验基线与代码状态，不能简单相加或相乘。

**失败条目详述（这是本阶段最值得记录的一条）。** host tiling 从输入张量形状反推
请求边界：二维输入 + decode 模式一律先读成「每请求一个 token」，只有当「形状给的
请求数」与「偏移表给的请求数」对不上时才改用偏移表。变长路径传的恰是二维 packed
批次——一个请求占满整段校验窗口、旁边一串零长度行。`[8,0,0,0,0,0,0,0]` 这一组：总
token 8，偏移表给的请求数 `9-1=8`，形状给的也是 8，**两者相等，回退条件不触发**，
偏移表根本没被读。

于是算子给第 i 行派窗口 `{start=i, len=1}`：第 0 个 token 在两种读法下都是第 0
行的第一个 token，**结果正确**；第 1–7 行的 cache index 是 -1，整行被跳过，对应
输出**一个字节都没被写**。按该测例参数推算，512 个输出元素里 448 个是未初始化显
存（数值每次不同，像测试不稳定），状态侧 slot 1 的 offset 3–9 共 448 个元素未被
覆盖，而 offset 0–2 两边完全一致。

四组参数里只有这一组失败，原因可以列成表：

| lengths | 总 token | 偏移表给的请求数 | 形状给的请求数 | 回退触发 | 结果 |
| --- | --- | --- | --- | --- | --- |
| `[8]` | 8 | 1 | 8 | 是（1≠8） | 走变长，正确 |
| `[3,1,4]` | 8 | 3 | 8 | 是（3≠8） | 走变长，正确 |
| `[1,1,1]` | 3 | 3 | 3 | 否（3=3） | 但「每请求一个 token」本就为真，两种读法一致 → 正确 |
| `[8,0,0,0,0,0,0,0]` | 8 | 8 | 8 | 否（8=8） | **错** |

它是唯一同时满足「token 数 = 请求数」且「长度不全为 1」的组合。而 ragged 全图的
固定捕获形状会让这种相等成为常态——这解释了为什么它在整网里能藏住：只有补齐空位后
恰好相等的批次才错，错的还只是后续 token，首 token 永远正确，输出读起来依然通顺。

**图 5 偏移表没被读时，算子给第 i 行派的窗口是 `{start=i, len=1}`：首 token 因为
输入相同而仍然正确，其余 token 落在被跳过的空行上。**

**第二层失败更值得记。** 把推断规则改对之后，设备上毫无变化。原因是：改规则实际
改的是某个 `inline` 函数的函数体，而三个共享 tiling header 把包括它在内的全部
helper 都放在同一个命名空间；原有的 op type 宏重命名只换了一个 token，命名空间与
函数名都没动。两个编译单元于是发出相同符号、不同实现——链接器只保留一份、丢掉另一
份且不给诊断，设备上留下的是原版那份。**策略是否生效，取决于编译器是否内联一个约
两百行的函数。**

定位靠两件事：一个探针（一个 8 token 请求配 7 个空位，回来是第 0 个 token 匹配参
考、第 1–7 个从未被写过），和一个两编译单元的最小复现例（`-O0` 下设了策略的单元
用的是另一个单元的实现，`-O2` 下函数被内联、各自保留自己的）。修法是给新算子的编
译单元换独立命名空间，并在共享 header 加编译期检查：**开了策略却没换命名空间，直
接编译失败。**

#### 4.1.4 为什么此时进入下一阶段

独立 golden 覆盖了公式、数据类型、零长度行与「历史选择器超过当前宽度」，并且多轮
之间用 golden 状态续接而从不从被测算子回种。它不覆盖的是真实环境的地址、并发、资
源与整网的批次组成——那些只能在整网里验证。

### 4.2 W1/W2：eager 整网等价与真实 cost table

#### 4.2.1 合同

- 基线是**同一引擎去掉 manager**：`method: dspark` +
  `enable_adaptive_verification: false`。基线不调用 AV 的任何代码路径。
- 判据是逐 token 相等，但**仅当参考自身可复现**（这条前提当时是假设，第 5.4 节证
  明它在更大规模下不成立）。
- 门禁不只看输出：一条 lane 还必须给出「真的裁过」和「置信度真的在动」的证据，否
  则一次相等只证明了基线等于自己。

#### 4.2.2 做法

**机制一：aggregated warn 行。** 两条 lane 都是诊断路径，需要在普通 `vllm serve`
日志里看到决策，又不能把整个进程拉到 DEBUG——TP=4 下每 rank 每步一行会把要找的失
败埋掉。做法是按窗口聚合，每 `interval` 步打印一行均值。一行里包含：窗口步数、平
均请求数、`scheduled_drafts` / `admitted` / `verify_tokens`、`kept%`、
`trimmed_steps`、最后一步的逐请求预算、`conf_moved=n/N`、`graph=<模式>=<次数>`。

`conf_moved` 是针对挑战 3 的专门探针：它统计窗口内有几步的 confidence buffer 真
的变过。`0/N` 就是冻结。这个数在设备侧累加，不给任何一步增加同步开销。

**机制二：异步 confidence 拷贝。** 首次整网跑出 **−11% TPOT 回归**。根因是
`record_confidences` 里一次阻塞的 D2H 拷贝——它把刚算出的 confidence 同步搬回
host，而 host 这一步并不需要它。改为侧流异步拷贝 + 设备侧修复非法值（`nan_to_num`），
单步由 18.10 ms 回到 16.09 ms。

**收益来自取消了一次主机等待，而不是拷贝变快了。** 上游本身就用双缓冲消费上一步
的 confidence，预算用的是 stale 值——既然如此，这次拷贝根本不需要被等待。

**机制三：真实 cost table 与可达区间判决。** 一旦进入图模式就不再注入合成曲线，
而是用启动时的 profile 填真实表，并把判决打印出来。关键细节是**只按服务可达的 Q
区间判断**：本服务最多呈现 `max_num_seqs × (K+1)` 个校验 token，超过捕获上限的 Q
是「离开图」的阶跃而不是「换到更便宜的 bucket」。按全部 profile 点报跨度，会把一
段平坦的可达区间说成陡峭曲线。

#### 4.2.4 为什么此时进入下一阶段

eager 已经固定了公式、状态、预算来源与日志口径，cost table 也证明可达区间有梯度。
但 eager 下的收益恒为零（第 1.2 节），要继续验证的假设全部关于**图描述符与状态
契约**——继续改策略层已无法触及，因此进入 W3。

### 4.3 W3：ragged 全图

#### 4.3.1 合同：六个 batch size 不是同一个数字

把它们当成同一个数字是本阶段的主要错误来源：

| 名称 | 含义 |
| --- | --- |
| `B_max` | 服务启动允许的最大请求数（`max_num_seqs`） |
| `B_live` | 当前这一轮真实存在的请求数 |
| `Q` | verifier 本轮实际处理的总 query token 数 |
| `B_graph` | 某张图描述符能容纳的请求数 = `min(Q, B_max)` |
| `B_fia` | Full Attention 实际看到的请求行数 = `B_live`，有 token padding 时 `B_live + 1` |
| `B_gdn` | GDN 状态算子的固定请求轴 = **`B_max`，所有 bucket 统一** |

`B_graph = min(Q, B_max)` 的理由：每个真实请求至少占一个 anchor token，所以一张
Q-token 的图最多容纳 Q 个真实请求，同时不超过服务最大并发。

**`B_gdn` 必须固定为 `B_max`**，这是挑战 1 的直接应对。即使当前只有 32 个请求，
后面的行也作为零长度、无效状态索引的空行保留——用一点 metadata 清理成本换所有图共
用同一套状态契约。

padding 行的契约（参考设计 §3.2.2 / §3.4.5）：长度为零、状态索引为 `PAD_SLOT_ID`、
算子跳过、padding token 不写入任何真实 KV 或 GDN 状态。**行被保留，不被截断。**

#### 4.3.2 做法

**机制一：固定 GDN 请求轴。** `gdn_attn_builder.py` 的 FULL speculative 分支在
AV 开启时用 `self.gdn_request_axis = max_num_seqs` 代替 `m.num_reqs`，并对超宽批
次加断言（宽度小于活跃请求数会静默丢行，那是唯一能真正破坏状态的方式）。

**机制二：FIA padding 行要有落脚处。** FIA 为每个 padding 请求保留满 K+1 的
query span，而 GDN 必须把它们当零长度看待——GDN 靠 `seq_lens == 0` 识别 padding
行，再把 query 视图在第一个 inactive 行截断。这里出过一次三连错，详见台账。

**图 4 同一个批次的两种视图：FIA 给每个 padding 请求保留满 K+1 的 query span，
GDN 必须把同样的行看成零长度、状态索引无效。**

**机制三：拒绝不纯批次，且不复述 vLLM 拥有的东西。** ragged 全图的契约是纯投机解
码。判别方式是比较 `num_scheduled_tokens` 与 `scheduled_spec_decode_tokens` 的长
度——一个正在 prefill 的请求出现在前者而不在后者，两个长度恰好在批次混合时不等。
拒绝的实现刻意做成**无签名依赖**：用 `dataclasses.replace` / `_replace` 改写描述
符的 `cg_mode`，不重述 vLLM 的字段表或函数签名。

**收益来自消除「裁剪后掉出图」这一个惩罚，而不是创造一个新的梯度。** 这句判断来
自旁证：全程 FULL 的 lane 耗时 256 s，全程 PIECEWISE 的 lane 250 s——PIECEWISE 反
而略快。若出图有数量级的稳态惩罚，总耗时会明显拉开。

#### 4.3.3 实验台账

| 实验 | 主要变量 | 结果 | 决策 | 说明 |
| --- | --- | --- | --- | --- |
| uniform 图描述符 | 让未裁剪批次回放定宽 decode 图 | bs=4 MATCH | 接受为中间站 | 裁剪批次仍掉回 piecewise |

**三次回退的共同形状：在一个地方验证或修复，然后假定它在别处也成立。** 抄签名假
定「本地 checkout 等于部署版本」；照参考设计做假定「取其中一条路径等于实现了那一
节」（§4.5 的四条路径是一套，漏一条就有批次无人接管）；修脚本假定「修好一个脚本
等于修好这类问题」。

三道护栏据此落地，且都验证过会报警：

1. **版本**：以 `git show v0.28.0:<path>` 为唯一事实来源，锁定部署版本读源码；
2. **结构**：不在本仓代码里复述外部签名与字段表，改用 `dataclasses.replace` /
   `hasattr` 分流；
3. **一致性**：加一个 CPU 检查，解析两个脚本的 `child_env`，把「被显式清掉的 key

### 4.4 W4：收益对比

#### 4.4.1 合同

- 对比方式对齐该特性自己的 PR 的报告口径：同一 `--cudagraph-mode` 应用于两条
  lane，比的是「Target FULL」对「Target FULL + Dynamics」，不是两种图配置。
- 输出定长（`ignore_eos`），并硬检查两条 lane 的产出 token 数完全相等，否则 TPS
  不可比，直接报错。
- 噪声底来自**第二个固定 K 进程**，不是同一进程的第二次 generate。
- 数据集用 Dolly 而非 Math500——数学题的接受率整体偏高，可裁的空间更小，会低估也
  会误判收益来源。

#### 4.4.2 做法

单变量原则在这一阶段被反复用到。K 不是我们能变的量（checkpoint 固定），所以扫的
是并发而不是草稿数；`--max-num-batched-tokens` 这类会改变整个图配置的参数被从扫
描里移除，因为它让一次扫描变成多种配置的混比。

两处与「测什么」有关的修正值得记：

- **编译缓存**：缓存键不覆盖决定编译结果的全部输入（AV 路径会在配置定稿后改写
  `cudagraph_mode`），于是一条 lane 可能取到为另一种配置编出的产物，表现为图编译
  器报 unpack 数量不匹配而不是缓存未命中。两个脚本都必须设
  `VLLM_DISABLE_COMPILE_CACHE=1`。这一条先只在吞吐脚本里修了，门槛脚本漏掉，后来
  又崩了一次——这是第 4.3.3 节那条「两个脚本各自建引擎」的直接后果，也是第三道护
  栏的来由。
- **profiling 上下文**：一致性检查抓到吞吐脚本从未设置
  `VLLM_ADAPTIVE_VERIFICATION_PROFILE_CONTEXT_LEN`。进一步读消费方才发现，
  `set_dummy_context` 第一步就做 `min(context_len, max_model_len - query_len)`，
  两个脚本的 `max_model_len` 都低于上游默认 8192，**所以这个值一直等于
  `max_model_len`，显式设置是当前配置下的 no-op**，W4 的数字不受影响。这一条作为
  失败条目记录：发现了差异，但凭差异推演后果而没有去读消费它的代码。

#### 4.4.3 实验台账

| 实验 | 主要变量 | 结果 | 决策 | 说明 |
| --- | --- | --- | --- | --- |
| 固定 vs 动态（冻结版本） | `enable_adaptive_verification` | 441.3 → 457.3 toks/s（+3.6%），噪声底 0.6% | 接受 | 本报告唯一的正式结论 |
| Math500 数据集 | 换数据集 | 接受率整体偏高，可裁空间小 | 回退到 Dolly | 数据集选择会改变收益来源 |
| 扫 `--max-num-batched-tokens` | 同时变调度宽度 | 一次扫描混比了多种图配置 | 回退 | 单变量原则 |
| 让 AV 保留 piecewise | `KEEP_PIECEWISE` 默认翻为 1 | 收益看起来更大 | 回退 | 口径不公平（第 2.2 节） |
| 提高门槛灵敏度 | `--max-tokens` 64 → 256 | 没抓到 lane 缺陷，抓到参考自身不稳 | 接受该结论 | 见第 5.4 节 |

表中每个百分比对应当时的实验基线，不能简单相加或相乘。正式结论只采用第一行。

### 4.5 方法本身的工程化

这次实践的流程沉淀不是工具，是三条**约束**：

**约束一：门禁与被测对象不能由同一次改动同时调整。** 本实践出过一次反例——门槛脚
本的 `--graph` 被施加到每一条 lane 包括基线，于是基线也在编图，比较变成了两种图
配置之比。修法是让 `--graph` 按**值**而不是按 key 是否存在来判定。教训是：改了被
测对象，就不要在同一个提交里顺手改验收条件。

**约束二：退出码不能被管道吞掉。** 曾用 `pytest | tail -2` 看结果，管道让退出码
丢失，带着两个失败的测试推了一次提交。此后不再用任何会丢退出码的管道查看测试结果。

**约束三：失败后回到哪里归因是预先定义的。** 本实践的归因顺序是：先确认门禁本身
可复现（`baseline2` lane 专门做这件事），再确认 lane 真的生效（`conf_moved`、
`kept%`），最后才看输出。顺序反过来会把量具问题当成功能缺陷——第 5.4 节那次正是如
此。

`enable_adaptive_verification: false`，基线不调用 AV 的任何代码路径，也不构造
manager。两条路径使用同一台 910B4 四卡机、同一 vLLM v0.28.0、同一
`--cudagraph-mode FULL_DECODE_ONLY`、同一 `max_num_seqs=16`、同一
`max_model_len=4096`、同一 Dolly 采样方式和同一随机种子（`seed=17`）。基线是现有
生产路径，已被调优过，不是为了对比临时写的。

公平性六项自查：环境同一 ✅；配置对等 ✅（图模式同时施加于两条 lane，且这一条曾
经出错并修复）；输入同一 ✅（同一数据集、同一偶数步长采样、同一种子）；预热对等
✅（见下）；实现成熟度 ✅（基线是生产路径）；口径同一 ✅（两边都是离线
`generate` 的端到端墙钟时间）。

**采集协议。** 每条 lane 与每个并发配置使用 **1 个独立进程**、进程内 **3 次计时
pass**。每个进程在计时之前先跑一次**被丢弃的预热 pass**（`max_tokens=8`），它承
载图捕获、cost table profiling 与全部惰性分配——把这些计入第一次计时会让均值依赖
重复次数。指标为 `总产出 token / 墙钟秒` 的 **3 次算术平均**，同时报 `max − min`
的极差。

**包含与不包含。** 这个数字**包含** prefill、调度、采样、拒绝采样、GDN 状态更新、
TP 通信与全部主机侧开销——它是离线 `generate` 的端到端吞吐。它**不包含**引擎加
载、图捕获、cost table profiling（都在被丢弃的预热 pass 里）。它**不是**设备侧
kernel 耗时，两者差一个量级，不可混用。

**定长保证。** `ignore_eos=True`，于是每种配置都恰好产出 `请求数 × 输出长度` 个
token，脚本对此做硬检查，不等则直接报错。因此 TPS 的差异只来自时间。

**噪声底。** 同一配置在**第二个进程**里再跑一次（`--control` lane），两者之差即
进程级噪声。**小于噪声底的差异不是结果。** 本次两个固定 K 进程之间相差 0.6%，这
就是噪声底。

**接受长度与时延口径。** 平均接受长度取自周期性 stat logger 的
`Mean acceptance length`（离线入口默认关闭，脚本显式打开）。单请求解码时延取自引
擎核心的单调时钟 `first_token_ts` / `last_token_ts`，**不混入**前端墙钟的
`arrival_time`。报 p50 / p99 / max，不报均值——负载一次性提交、定宽排空，均值约等
于总时长的一半，只是吞吐的换算，不含信息。

### 5.2 分层结果

#### 组件级：cost table

`max_num_seqs=16`、`graph_limit=128`、130 个 profile 样本：

| Q | 1 | 8 | 16 | 32 | 64 | 96 | 128 | 192 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| target 前向 (ms) | 29.05 | 33.58 | 37.46 | 42.33 | 48.27 | 53.81 | 59.25 | 217.84 |

可达区间（Q ≤ 128）跨度 **30.20 ms**，判决为「随 Q 变化，更小的预算能落到更便宜
的 bucket」。Q=192 的跳变是离开捕获上限、失去图，属于阶跃而非梯度，不计入可达跨
度。

固定部分 29.05 ms 与可变部分 30.20 ms 几乎相等——**这是全篇最重要的单个事实**，第
5.3 节用它解释收益规模。

#### 端到端

| 指标 | 固定 K 基线 | AV 开启 | 变化 |
| --- | --- | --- | --- |
| 吞吐 (toks/s) | 441.3 | 457.3 | **+3.6%** |
| 进程级噪声底 | — | — | 0.6% |
| 平均接受长度 | 3.33 | 3.22 | −3.3%（按设计） |
| 推得单步时间 (ms) | 117.7 | 109.8 | **−6.7%** |
| 批次占用 | 15.6 / 16 | 15.6 / 16 | 饱和，无变化 |
| 单请求解码 p99 (ms) | 12.89 | 12.84 | −0.4% |

表中各项来自**同一次冻结对比**，共用一个基线，因此可以放在一起读；但它们不是同向
可加的——单步 −6.7% 与接受长度 −3.3% 是两个相反效应，第 5.3 节给出它们相乘得到净
值的算式。过程中各轮实验的百分比不在此表内，也不能并入。

**收益 +3.6% 是噪声底 0.6% 的六倍**，差异成立。单步时间是推算量（`接受长度 / TPS`），
不是直接测量，标注为推得。

#### 接入验证

痛点计算预测：aggregated 行里必须出现 `kept` 低于 100% 的窗口，且与 `graph=FULL`
同窗口共现。实测 aggregated 行给出 `kept` 在 58%–100% 之间波动、48 个窗口中 12
个发生裁剪、`graph=FULL` 覆盖全部纯解码步、`conf_moved` 为满值。

三种异常的含义都在脚本里有对应判定：`kept` 恒为 100% → lane 构造了但从未裁剪，标
记为 INCONCLUSIVE；`conf_moved` 为 0/N → 置信度冻结，标记为 FAIL；出现
`graph=NONE` 的步数应当等于含 prefill 的步数（`verify_tokens > admitted + num_reqs`
单独计数为 `prefill_steps`），超出则说明纯解码批次也掉出了图。

解码步 100% 命中全图]

#### 正确性

| 层次 | 覆盖 | 不覆盖 | 结果 |
| --- | --- | --- | --- |
| 独立 FP64 参考逐点比对 | 公式、数据类型、零长度行、历史选择器超宽 | 真实地址、并发、资源 | 5/5 通过，状态按位 |
| 多轮状态续接 replay | 状态累积、缓冲代际覆盖、写回顺序 | 端到端质量 | 通过（golden 状态续接，从不回种） |
| CPU 单元测试 | 构造签名、buffer 宽度、拒绝判据、两脚本配置一致性 | 设备行为 | 49 函数 / 77 用例全绿 |
| 整网逐 token 等价 | 批次组成、调度、图回放 | — | **在大规模下判据不成立**，见 5.4 |

#### 效率

[待补：本实践的实际人力投入，以及传统路径的项目估算。两者不是严格受控实验，仅作
项目估算与经验对照]

可以确定的效率结论是**哪些变化缩短了定位路径**，这些有机制支撑：

1. **先建独立 golden 再上设备**：`[8,0,…]` 那个 bug 是算子 host tiling 的问题，
   整网里它表现为「输出通顺但质量差」，无法定位；独立 golden 一次就指到具体行与
   具体元素。
2. **aggregated warn 行而非 DEBUG**：TP=4 下每 rank 每步一行会埋掉要找的失败。
3. **先判 cost table 再谈收益**：避免在 eager 下花时间优化一个在性能上无意义的决
   策。
4. **单变量 + 台账**：三次回退都能立即归因，没有出现「几项优化同时进一个 patch
   然后不知道哪项有效」。

### 5.3 为什么收益不等比例传导

58% 的校验 token 被白算，最终只换来 3.6% 的吞吐提升。这不是坏消息，但必须解释清
楚剩下的时间在哪。

**第一层：裁剪只能触及单步时间的约四分之一。** cost table 显示 Q=128 时 target
前向 59.25 ms，其中 29.05 ms 是与校验 token 数无关的固定成本。对照推得的 117.7
ms 单步：

```
target 前向        59.25 ms  ≈ 单步的 50%
  其中固定部分     29.05 ms  ≈ 单步的 25%   ← 裁剪碰不到
  其中可变部分     30.20 ms  ≈ 单步的 26%   ← 裁剪唯一能碰的
前向之外           58.5  ms  ≈ 单步的 50%   ← 裁剪碰不到
```

**图 2 裁剪唯一能触及的是单步 117.7 ms 里的 30.20 ms（26%）——target 前向的可变部
分；固定成本 29.05 ms 与前向之外约 58.5 ms 都碰不到。**

**第二层：裁剪从不减少起草的工作量。** 读 v0.28.0 的 DSpark speculator 可以确认：
草稿不是 K 次模型前向，而是一次 backbone、一次 `compute_draft_logits` 产出全部
K 个位置，然后 K 次很轻的 markov 偏置与采样循环；而那个循环是
`for i in range(n_spec)`，**预算完全不参与**。这是设计使然——预算正是从这次起草产
出的 confidence 算出来的——但它把天花板钉死了：草稿成本是 AV 永远碰不到的常量。

**第三层：裁剪要付接受率的代价。** 实测平均接受长度 3.33 → 3.22，即 −3.3%。所以
净收益是两个相反效应的差：

```
单步时间   −6.7%
接受长度   −3.3%
净吞吐     ≈ 1/0.933 × 0.967 − 1 ≈ +3.6%   ✅ 与实测一致
```

这个对账是本章最有价值的一行：**它说明收益的来源和规模都在预期内，而不是碰巧测到
的。**

**第四层：这个工作点对 AV 不利。** 固定成本的占比随批次规模下降。bs=16 时可变部
分只占 target 前向的 51%；参考设计在 bs=32 的测量里，可变部分占到约 78%。换言之
本实践一直在 AV 最吃亏的规模上测它。这给出一条可验证的预测：**提高
`max_num_seqs` 应当放大 AV 的收益。** 这条尚未实测。

### 5.4 正确性判据失效：本实践最重要的负面结果

W1 到 W3 全程使用「与固定 K 基线逐 token 相等」作为正确性判据，并多次据此判定
MATCH。W4 阶段发现这个判据在服务规模下不成立。

证据链：

1. 同一 commit、同一配置，门槛脚本一次报 FAIL（token 2 分歧）、一次报 MATCH。两
   次运行共享同一个基线缓存键（键里含 git HEAD），所以不是代码差异。
2. 把门槛改成「同一引擎内采 8 次基线」：**8 次产出 4 种不同输出，最早分歧在
   token 2，且发生在一条此前一直稳定的 prompt 上。**
3. 这次运行里**没有任何 AV 代码**——前缀缓存关闭、异步调度关闭、greedy 带固定种子
   、基线连 manager 都不构造。

因此 09-23 那次 token-2 FAIL 是**量具读数，不是 AV 缺陷**。这条待办以「判据不成
立」而非「功能被证清白」的方式关闭。

**图 6 两次基线采样之间在 token 29 就分歧，而 lane 与其中一次一致到 token
204——lane 比参考的两次采样之间更接近。**

同一组数据对 AV 是正面的：把 lane 与各个基线 pass 逐一比对，lane 与某一个 pass
一致到 **token 204**，而两个基线 pass 之间只一致到 **token 29**。**lane 比参考的
两次采样之间更接近。** 这是「AV 未引入自身漂移」的直接证据，但它不是等价性证明。

据此门槛判据被重新定义：基线从「一个参考」改为「一组 pass」，lane 与每一个比；复
现任意一个 pass 记为 MATCH；噪声底取全集里最早分歧的那一对；`_worse` 只有一份定
义，噪声底与每条 lane 判据共用，使 lane 不会被一条噪声底没量过的规则判死。并新增
一个**只测参考**的模式（不建 speculative config），用于在判定任何 lane 之前先确
认采样 token 相等在该配置下是否还能当工具。

剩下的未决问题是**这份不确定性属于谁**——它在去掉投机解码后是否还存在，尚未测量。
候选是批次形状相关的 kernel tiling 与 TP=4 的归约顺序。

## 7 亮点与局限

### 7.1 亮点

每条亮点都写成可迁移的判断，并附适用条件。

**亮点 1：「能裁」和「有收益」是两件事，先量后者。**

AV 的策略层再准，如果 cost table 在服务可达的 Q 区间内是平的，裁剪就不改变单步时
间，controller 没有可优化的目标。本实践把这件事做成启动时的一行判决，而不是靠人
猜。**适用条件**：任何「少算一些工作换时间」的优化都适用——但前提是你能把成本曲线
测出来。成本曲线不可测时，这条判断退化为经验。

**亮点 2：对有状态算子，shape 变化不只是性能问题，还会改变状态读写契约。**

这是本实践最反直觉的一条。对无状态算子，缩小 shape 通常只影响速度；GDN 这类循环
状态算子，请求轴一变，状态的读写位置就变了。**代价换法是明确的**：用一点
metadata 清理成本（钉死 `B_gdn = B_max`，保留零长度空行）换所有 bucket 共用一套
状态契约。**适用条件**：有持久状态、且状态索引由 shape 推导的算子。无状态算子不
必付这个成本。

**亮点 3：输出对比抓不到「策略层静默失效」，必须单独做活性探针。**

裁剪只是策略，拒绝采样仍然正确，所以置信度冻结时输出逐 token 不变。任何等价性判
据都抓不到它，唯一症状是「特性看起来没效果」。`conf_moved=n/N` 这类探针的成本极
低（设备侧累加，不加同步），收益是把一个能藏几周的问题变成一行日志。**适用条件**：
任何「只影响决策、不影响结果正确性」的优化——这类特性的失效模式天然不可观测。

**亮点 4：量具必须和被测对象一样被怀疑。**

本实践花了相当篇幅追一个「间歇性正确性缺陷」，最后证明是判据本身在该配置下不成立。
更值得记的是归因顺序：先确认门禁可复现，再确认 lane 真的生效，最后才看输出。顺
序反过来就会把量具问题当成功能缺陷。**适用条件**：任何依赖「逐点相等」做验收的场
景，尤其是多卡归约、动态批次这类本身不保证位级可复现的系统。

**亮点 5：不要在本仓代码里复述外部仓库拥有的签名与字段表。**

两次回退都源于按本地 checkout 的签名写调用，而部署版本不同。结构性的修法不是「记
得对版本」，而是**让代码不需要知道签名**——用 `dataclasses.replace` / `hasattr`
分流，用 `git show <tag>:<path>` 作为唯一事实来源。**适用条件**：跨仓依赖且版本
锁定的工程；单仓项目不必付这个抽象成本。

### 7.2 局限与遗留

**已知不成立的条件。**

- 逐 token 等价判据在 `max_num_seqs=16`、256 token 输出规模下不成立（8 次采样 4
  种输出，最早分歧 token 2）。小规模（bs=4、64 token）下它看起来成立，但据此得出
  的 MATCH 结论都是「单次采样对单个参考样本」，强度弱于本报告此前的呈现。
- 混合批（含真实 prefill）离开 ragged 全图走 eager，约 9% 的运行时间在图外。这是
  设计选择而非缺陷——参考设计把混合批留给「eager 或原生安全组合路径」，并把
  prefill/decode 拆微批列为未来工作。
- `+3.6%` 只在 `max_num_seqs=16`、Dolly、输出定长 256 token 下测得。固定成本占比
  随批次规模下降，所以这个数字很可能是该特性在本平台上的**下界**而非典型值。

**未验证的推广。**

- 「提高 `max_num_seqs` 会放大收益」是基于 cost table 结构的预测，**未实测**。
- 随机采样路径未验证，全部结论基于 greedy。
- 本报告的人力投入数字缺失（见 5.5 的待补），没有效率倍数可引用。
- 单步时间 117.7 / 109.8 ms 是由 TPS 与接受长度**推算**，不是直接测量；用于机制
  对账，不应作为单步性能指标引用。

**遗留技术债。**

- 参考设计清单第 5 项（概率绑定 graph descriptor、每轮只消费一次）未做。判断：只
  影响随机采样，greedy 路径不受影响，可暂缓。
- 清单第 6 项（drafter 未使用 KV tail 的 slot mapping 置无效）未做。判断：残留写
  入的是 draft KV，只压接受率、不改输出（greedy 下被拒草稿一律由 target 的
  argmax 取代），所以它是性能项而非正确性项，可暂缓——但它会压低接受率，因此**本
  报告的 3.33/3.22 两个数都可能偏低**。
- FIA sink 接 `UpdatableGraph` 的钩子在一次 rebase 中丢失，未补回。
- 两个脚本仍各自构造引擎，一致性靠一个 CPU 检查兜住。更干净的做法是共用一个引擎
  构造函数，本轮未做。

**下一步值得验证的三个假设。**

1. 去掉投机解码后，参考在 TP=4 下是否仍不可复现——这一刀决定那份不确定性是平台的
   还是本实践路径的，门槛脚本已具备 `--no-spec` 模式，尚未运行。
2. 算子级 profile 里，单步那 50% 的非前向时间具体由什么构成；特别是设备上是否存
   在空隙（若有，瓶颈是主机下发，解法与裁剪无关）。基准脚本已具备
   `--profile-dir`，尚未运行。
3. `max_num_seqs=32` 下 AV 的收益是否超过 bs=16 的 +3.6%（判定门槛同第 3.1 节：
   至少为当次噪声底的 3 倍），用以验证第 5.3 节第四层的预测。

### A 术语与缩写

| 术语 | 含义 |
| --- | --- |
| AV（adaptive verification） | 自适应校验。按每个草稿位置的存活概率，逐请求裁掉注定被拒的草稿，使校验批次变短 |
| DSpark | 本实践使用的投机解码方法，草稿宽度 K 由 checkpoint 固定 |
| K / `num_speculative_tokens` | 每请求每步的草稿数。本实践 K=7，校验宽度 K+1=8（含 bonus token） |
| bonus token | 校验批次里属于上一步已确定 token 的那一个，每请求恒有一个 |
| 接受长度（acceptance length） | 每请求每步最终产出的 token 数，含 bonus。本实践 3.22–3.33 |
| GDN（Gated Delta Net） | 带循环状态的注意力替代结构。Qwen3.6 的混合结构里包含 GDN 层 |
| FIA | Full Attention 一侧的实现路径，与 GDN 并存于同一模型 |
| cost table | 启动时 profile 得到的「校验 token 数 → 单步成本」查找表，controller 的 argmax 依据 |
| Q | verifier 本轮处理的总 query token 数 |
| ragged（变长） | 逐请求 query 长度不等的批次几何 |
| PIECEWISE / FULL | ACL Graph 的两种捕获模式；FULL 整图回放，PIECEWISE 按切分点分段 |
| `FULL_DECODE_ONLY` | 纯解码批次走 FULL、其余走 NONE（即 eager）的组合模式 |
| capture / replay | 图的捕获与回放 |
| graph_limit | 最大被捕获的尺寸，超出则离开图 |
| fallback | 批次不满足图契约时退回的执行路径 |
| `PAD_SLOT_ID` | 标记「这一行没有有效状态槽位」的哨兵值（−1） |
| `conf_moved` | 诊断字段，窗口内置信度 buffer 真正变化过的步数 |
| `kept%` | 诊断字段，`admitted / scheduled`，裁剪强度 |
| 噪声底（noise floor） | 同一配置在第二个进程里重测得到的差异，小于它的差异不是结果 |
| ODR / vague linkage | C++ 的单一定义规则；`inline` 函数允许多个编译单元各有定义，链接器只保留一份 |
| TPOT | time per output token，单 token 产出时间 |
