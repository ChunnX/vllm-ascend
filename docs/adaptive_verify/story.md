# `8 = 8`

一次 Ascend 上的动态校验接入，和四个看起来像答案的阶段

## 一、一个没人用的预测头

这件事开始的时候，手里只有一个闲置的权重。

DSpark 的 checkpoint 里带着一个 confidence head，训练时学的是「这个草稿位置会不会被接受」。我们这条路径上它从来没被读过：草稿宽度写死 K=7，每个请求每步固定送 8 个 token 进校验，7 个草稿加 1 个必得的 bonus。

为什么值得去碰它，看一组实测就够了。K=7、96 并发下，草稿按位置统计的接受率是这样的：

| 位置 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| ceval | 77.1% | 56.1% | 41.5% | 31.2% | 23.3% | 17.6% | 13.1% |
| gsm8k | 83.7% | 66.9% | 56.2% | 47.2% | 39.6% | 33.1% | 27.4% |

第七个位置在 ceval 上只有 13.1% 的机会被接受，却和第一个位置一样占满一个校验槽位。后三个位置加起来贡献 0.54 个 token，占掉 3/7 的槽位。

上游已经把算法写好了：按置信度的前缀累乘排序，枚举保留多少个草稿，取「预期接受数除以预计耗时」最大的那个。K 由 checkpoint 固定，调不了，所以能动的只有这一处。

缺的是中间那一层。裁剪之后每个请求的 query 长度不再相等，而这条路径上的 GDN 算子、图描述符、状态契约，全都是按「每请求恰好 K+1 个 token」写的。

还有一层约束，是动手之前就该知道的。参考复盘里有一张表，记录了同一条路在另一条草稿方法上走过的结果：eager 模式下 capture_size 从 16 到 512，单步成本分别是 84.25、80.18、79.31、79.88 毫秒。

曲线是平的。Q 从 16 到 512 没有可区分的代价差异，意味着在 eager 下，controller 选哪个预算，单步时间都一样。那张表只写了「measured on one model」，没有型号也没有并行度，所以我们只引用它的相对关系。但相对关系已经足够：图外的固定开销在 eager 里占主导，裁剪要换到时间，先得入图。

于是路线定了下来：先让算子接受变长输入，再让变长批次能回放已经捕获的图，最后才谈收益。

## 二、`[8, 0, 0, 0, 0, 0, 0, 0]`

入图的第一件事是让算子接受变长输入。

固定 K 路径上的两个 AscendC 算子，一个做因果卷积，一个做循环状态更新，都隐含「每请求恰好 K+1 个 token」。差异集中在两个入参：长度从 `actual_seq_lengths` 换成 `query_start_loc` 的 cumsum，状态索引不再 `.flatten()`，保留 `[B, S]` 的二维形状。扁平化之后寻址只能按固定 stride 隐式推算，保留二维，每行用掉的列数才可以不同。

正确性交给一组独立的 FP64 NumPy 参考，不调用任何 kernel，多轮之间用参考自己的状态续接，从不从被测算子回种。

四组参数里，三组通过，`[8, 0, 0, 0, 0, 0, 0, 0]` 失败。

这一组是一个请求占满全部 8 个 token，旁边跟着 7 个长度为 0 的空位。失败的形态很奇怪：不报错，第 0 个 token 完全正确，第 1 到第 7 个是随机数值，而且每次运行都不一样。

它看起来像一个不稳定的测试。

根因在 host 侧的 tiling。算子跑起来之前，有一段主机代码要先从张量形状推断出「这一批有几个请求、每个请求几个 token」。它的规则是：二维输入加 decode 模式，一律先读成「每请求一个 token」；只有当形状给出的请求数和调用方传的偏移表对不上时，才改用偏移表。

这个规则有一个没有写在代码里的假设：形状和偏移表对不上，是变长批次唯一的识别特征。

而这一组里，总 token 数是 8，偏移表给出的请求数是 8，形状给出的请求数也是 8。

两个数相等，回退条件不触发，偏移表根本没有被读。

算子于是给第 i 行派了窗口 `{start=i, len=1}`。第 0 个 token 在两种读法下都是第 0 行的第一个 token，输入完全一样，所以它是对的。第 1 到第 7 行的状态索引是 pad 哨兵，整行被跳过，对应的输出从未被写入。测试读到的是未初始化显存。

四组参数里为什么只有它命中，列出来一目了然：

| lengths | 总 token | 偏移表给的请求数 | 形状给的请求数 | 回退触发 |
| --- | ---: | ---: | ---: | --- |
| `[8]` | 8 | 1 | 8 | 是 |
| `[3,1,4]` | 8 | 3 | 8 | 是 |
| `[1,1,1]` | 3 | 3 | 3 | 否，但两种读法本就一致 |
| `[8,0,0,0,0,0,0,0]` | 8 | 8 | 8 | 否 |

它是唯一同时满足「token 数等于请求数」和「长度不全为 1」的组合。

更要紧的是最后一列背后的事：变长全图的捕获形状是固定的几档，批次要向上补齐到档位，于是「token 数等于请求数」在真实服务里不是边角情况，是常态。这个 bug 会反复触发，而症状是首 token 正确、后面乱掉、输出读起来还通顺。

修法是给共享的 host tiling 加一个开关：这个算子永远以偏移表为准，不再猜形状。开关只在新算子的编译单元里打开，原算子行为一字不变。

## 三、改对了，但跑的不是它

改完，重新编译，重新安装算子包，上设备。

行为一点没变。

探针打到装好的算子上问了一次：一个 8 token 的请求配 7 个空位，回来仍然是第 0 个 token 匹配参考，第 1 到第 7 个从未被写过。和改之前一模一样。

那个开关改的是一个函数的函数体。这个函数叫 `GetShapeDtypeInfo`，和原算子共用同一个命名空间，而且被声明成 `inline`。原有的重命名只换了 op type 这一个 token，命名空间和函数名都没动。

两个编译单元于是发出了相同的 mangled symbol，各自带着不同的实现。这是一次 ODR 违反，而 `inline` 意味着 vague linkage：链接器会保留其中一份，丢掉另一份，并且不给任何诊断。

设备上留下来的，是原版那一份。

这个开关到底生不生效，取决于编译器要不要内联一个大约两百行的函数。

为了确认机制，我们另外写了一个只有两个编译单元的最小例子：不开优化时，设了开关的那个单元用的是另一个单元的实现；开了优化之后函数被内联，两个单元各用自己的。同一枚看编译器心情的硬币。

修法是给新算子的编译单元换一个独立的命名空间，让符号不再重名。同时在共享 header 里加一道编译期检查：开了开关却没换命名空间，直接编译失败，不再有被静默丢掉的可能。

这是第一次，问题从「算子算错了」收缩成了一条可以指着构建规则说清楚的边界。

## 四、三分之一个契约

算子对了，接下来是图。

ragged 全图要求所有档位共用同一套状态契约，其中最硬的一条是 GDN 的请求轴固定为服务允许的最大并发，而不是跟着当前活跃的请求数走。对无状态算子，shape 变小往往只是性能问题；GDN 是循环状态算子，请求轴一变，状态的读写位置跟着变。

我们把轴钉死了，然后在服务规模上第一次拿到了有梯度的 cost table：16 并发下可达区间跨度 144 毫秒，32 并发下 263 毫秒，Q=64 处多八个 token 要多付 81 毫秒。裁剪确实能落到更便宜的档位，这一条从类比变成了实测。

可这两轮跑出来的输出，都和基线对不上。

首要嫌疑恰恰是刚钉死的那条轴。它在「最大并发等于活跃请求数」的时候是个空操作，而那正是它被引入时面对的形状，所以看起来无害。到了 16 和 32 并发，活跃请求只有两到四个，轴却钉在最大值上，这是它第一次真的产生 padding 行。

而它所属的那份契约，是和注意力侧的请求轴、以及持久 seq_lens 镜像里的 padding 清理一起成立的，三处改动来自同一份复盘。

只实现其中一条，不是更安全的做法，是一个半成品。

于是把它改回 opt-in，默认退回到已经验证过的逐档位轴，等其余几条一起落地再打开。门槛脚本加了一个 `+axis` 后缀，下次可以直接二分它，而不是靠推理。

这一节的教训，在三天后又原样重复了一次。

## 五、−11%

轴的事先放一放，这时候回头看一个更早就该解释的数字。

接上预测头之后跑的整网，TPOT 回归了 11%。

方向是反的。裁剪少算了 token，单步应该更便宜。

定位到 `record_confidences` 里一次阻塞的 D2H 拷贝。它把刚算出来的置信度同步搬回 host，而 host 这一步并不需要它：上游的预算用的本来就是上一轮的值，双缓冲消费的是 stale 数据。改成侧流异步拷贝，设备侧顺手把非有限值修掉，单步从 18.10 毫秒回到 16.09 毫秒。

收益来自取消了一次主机等待，不是拷贝本身变快了。

这件事还留下一个顺带的发现：host 用上一轮的置信度定总预算，设备用本轮的置信度分每个请求的名额。这个代差不是疏忽，是让 host 永远不必等 drafter 的设计选择。代价是 CPU 侧看到的置信度，相对它正在为之定预算的那批草稿，又滞后了一代。

## 六、16 和 17

契约的其余几条陆续补上，轴重新钉了回去，ragged 全图在设备上跑了起来。

然后报了一个张量形状不匹配：`16 vs 17`。

来源是 FIA 的 padding 行。Full Attention 在有 token padding 时会多出一行，而逐请求的 buffer 只按 `max_num_reqs` 分配，那一行没有地方落脚。

把 buffer 加宽一行，不匹配消失了。

然后我们顺手做了第二件事：把 padding 行的 `seq_lens` 清零，让它在语义上也是一个空行。

这是错的。

清零之后出现了正确性回归。原因是 GDN 侧有一个函数靠 `seq_lens == 0` 识别 padding 行，然后把 query 视图在第一个 inactive 行处截断。在清零之前，这个条件恒为假，函数从未真正执行过；清零让它第一次生效，GDN 的请求轴于是从固定的 `B_max` 变成了跟着活跃请求数走。

而「所有图档位共用同一个请求轴」正是入图契约里最硬的一条。对无状态算子，shape 变小往往只是性能问题；GDN 是循环状态算子，请求轴一变，状态的读写位置跟着变。参考复盘记录过这个故障的样子：并发由小到大爬升时，前面几批请求短输出或者乱码，并发稳定之后自己恢复。不报错，而且会自愈。

我们把清零回退了，并在原处留了一句注释说明为什么不能清。

方向错在更前面一步。重读参考复盘的 §4.5 才看清楚：那一节给的是四条并列的路由规则，纯投机解码进 ragged FULL，未裁剪的常规 decode 进原版 uniform FULL，含真实 prefill 的批次离开 ragged FULL。我们只实现了其中一条，于是总有一类批次没人接管，而我们试图用加宽和清零去兜住它。

真正要做的是让混合批离开。判别方式是比较「本轮被调度的请求」和「本轮带投机草稿的请求」两个集合的大小，一个正在 prefill 的请求出现在前者而不在后者，两者恰好在批次混合时不等。

去处有两个候选，而这个选择影响的是后面所有测量的口径。

"我们不能回退 piecewise，piecewise 的话还得多编译很多张图，对显存也是很大压力。"

还有一层理由：动态校验关闭的时候，混合批同样走 eager。如果只让开启的时候享有 piecewise，测出来的差值里就混进了一个配置选择。所以被拒绝的批次落到配置本身给的去处，`FULL_DECODE_ONLY` 下就是 eager。

代价是明确的：这部分批次的时间仍然在图外。

## 七、679 个提交

同一段时间里还有两次崩溃，本来都不该发生。

第一次是 `'list' object has no attribute 'update_stream'`。我们想给图管理器加一个判断，于是照着工厂函数的签名重写了它的构造调用，而 `model_runner` 其实是第五个位置参数。

第二次是 `CudaGraphManager.dispatch() takes from 5 to 6 positional arguments but 7 were given`。

第二次之后才去对了版本：本地的 vLLM checkout，比部署用的那个 tag 领先 679 个提交。签名早就变了。

"我们 vLLM 需要钉死 v0.28.0 版本。"

从那以后，读源码一律 `git show v0.28.0:<path>`，而且本仓代码里不再复述任何外部仓库拥有的签名和字段表。改写图描述符的那段代码最终写成了没有签名依赖的形式，用 `dataclasses.replace` 和 `hasattr` 分流，不去记住字段有哪些。

这个形状前面已经出现过两次：钉死请求轴时假定它在别的并发下也无害，加宽 padding 行时假定补住一个症状等于实现了那条规则。抄签名是第三次，假定本地 checkout 等于部署版本。

而这些崩溃每一次都要有人去设备上跑一轮才能发现。

"你能不能确保没问题再提交，不然我验证的时间成本太大了。"

## 八、同一个 commit，一次 MATCH 一次 FAIL

功能面闭合之后，开始量收益。

正确性门槛的做法是：同一个引擎去掉动态校验的 manager 作为基线，两边跑同样的 prompt，逐 token 比对。bs=4 通过，bs=16、2 个 prompt 通过，4 个 prompt 也通过。宽请求轴被 13 个 padding 行真实行使过。

吞吐这边，冻结版本的对比是 441.3 对 457.3 toks/s，提升 3.6%，而同配置第二个进程测出的噪声底是 0.6%。收益是噪声的六倍。接受长度从 3.33 降到 3.22，p99 单请求解码时延没有恶化。

看上去，可以收尾了。

然后同一个门槛，在同一个 commit、同一个配置下，上午报 FAIL，下午报 MATCH。

两次运行共享同一个基线缓存键，而那个键里含 git HEAD。不是代码差异。

FAIL 那次的分歧出现在第 2 个 token。

## 九、8 次采样，4 种输出

第一反应是提高单次运行的灵敏度，而不是重复跑。把输出长度从 64 拉到 256，同一个引擎里多采样大约四倍的 decode 步。

结果是：lane 通过了，而基线自己没通过。

基线跑了两遍，两遍在第 29 个 token 上分歧。更有意思的是，lane 的那一遍和基线的第二遍在第 29 个 token 处给出了完全相同的四个 token。

看起来 lane 复现了基线的第二次采样。

这也是错的。把全长逐 token 比完才发现，lane 和基线第二遍在 token 204 处才分开。三条轨迹，两两不同。

于是把门槛改成只测参考自己：同一个引擎里连续采样 8 次，什么 lane 都不跑。

8 次采样，产出 4 种不同的输出，最早的分歧在第 2 个 token。

这次运行里没有任何动态校验的代码。前缀缓存关闭，异步调度关闭，greedy 带固定种子，基线连 manager 都不构造。

逐 token 等价在这个规模下不是一个可用的正确性判据。上一节那次 token-2 的 FAIL，是量具的读数，不是功能的缺陷。

这条待办因此关掉了，但关掉的方式不是「功能被证清白」，而是「判据不成立」。两者差别很大，所以必须写清楚。

同一组数据里也有对功能有利的一面：lane 和某一次基线采样一致到第 204 个 token，而两次基线采样之间只一致到第 29 个。lane 比参考的两次采样彼此之间更接近。这是「动态校验没有引入自身漂移」的证据，不是等价性的证明。

判据随后改成了参考集比对：基线从一个参考变成一组 pass，lane 与每一个比，复现任意一个记为通过；噪声底取全集里最早分歧的那一对。还加了一个只测参考的模式，在判定任何 lane 之前，先确认采样 token 相等在这个配置下还能不能当工具。

至于这份不确定性属于谁，去掉投机解码之后是否还存在，我们还没有测。

## 十、台阶

收益那边也出了事。

团队内部另一组对照，4 个数据集乘 5 档并发，指标是 TPOT 和端到端。32 并发及以上，TPOT 下降 3.3% 到 13.6%。

16 并发那一档，四个数据集全部是轻微退化，0.9% 到 1.7%。

和我们自己在 16 并发测到的 +3.6% 符号相反。

两边数据集不同、指标不同、代码快照不同，而且那组数据每个格子只跑了一次，没有记预热和重复次数，没有噪声底可以引用。能确定的只有一件事：在 16 并发这个量级上，收益接近零且符号不稳定，谁的数字都不该当成定论。

但顺着这条线往回看，才看懂了一件更要紧的事。

图是按固定的几个尺寸预先捕获的，运行时批次会被向上补齐到下一个捕获档位再回放。所以 cost table 在捕获范围内是一个阶梯函数，而台阶的边界，就是那些捕获档位。

举一个例子说明这意味着什么。假设捕获了 56 和 64 两档，当前这一步有 64 个校验 token：

```
verify 成本
   │                  ┌─────────────   Q 落在 (56, 64] 一律按 64 这一档计价
   │                  │
   │     ┌────────────┘                Q 落在 (48, 56] 一律按 56 这一档计价
   │     │
   └─────┴────────────┴──────────────→  Q
        48           56              64
```

裁到 60，Q 仍然落在 (56, 64]，回放的还是 64 那张图。单步时间一点没变，而裁剪本身的开销照付。裁到 56，降一档，这一步才真的变便宜。

裁掉四个 token 收益为零，裁掉八个才开始有收益。

这件事改变了对两组数字的理解。16 并发下为什么是退化：并发小的时候，单步时间由与校验 token 数无关的固定开销主导，可达的 Q 区间里曲线接近水平，最优点落在不裁附近，而预算枚举和设备 top-k 的开销仍然要付。32 并发以上为什么进入平台而不继续上升：可降的档位由可裁空间和档位疏密共同决定，前者由逐位置接受率决定，不随并发变化。

gsm8k 为什么在所有并发下收益都最小，也在第一节那张表里：它的第 5 到第 7 个位置贡献 1.00 个 token，ceval 只有 0.54 个。可裁的空间差了近一倍。接受长度的降幅也最小，4.8%，其余三个数据集在 10.1% 到 11.4% 之间，两者逐数据集对应。

收益不是连续的。「这一步裁掉了 6% 的草稿」和「这一步省了 6% 的时间」之间没有任何关系。

这也改变了该怎么评估它。要问的不是「平均裁掉了百分之多少」，而是「有多少步真的落到了更低的一档」。而我们当前的日志回答不了后一个问题：它统计保留比例，不区分「裁了」和「裁了并且降了档」。这个计数还没有补。

## 尾声

回头看，每一个阶段都找到过看起来像答案的东西。

变长算子像答案，它让每行的长度可以不同，可是改对了的那份被链接器丢掉了，而丢的那一刻没有任何诊断。固定请求轴像答案，它让所有档位共用一套状态契约，可单独上它，在真的产生 padding 行的那个并发上就崩了。异步拷贝像答案，它修掉了 11% 的回归，但 eager 下的收益本来就是零。+3.6% 像答案，换一个并发符号就反了。

每一个都确实是答案，只是回答的不是同一个问题。

有一条教训出现了两次，中间隔了三天。钉死请求轴是契约里的一条，padding 行的处理是另一条，混合批的去处是第三条。两次我们都只取了其中一条，然后试图用加宽、清零这类局部修补去兜住剩下的部分。只实现契约的三分之一，不是更安全的做法，是一个半成品。

另一个形状也重复了三次：在一个地方验证过，就假定它在别处也成立。抄签名假定本地 checkout 等于部署版本，照复盘做假定实现一条路径等于实现那一节，修脚本假定修好一个脚本等于修好这一类问题。三次都付了对方一轮设备时间。

还有一条更难的。改对了不等于跑的是你改的那份。那个 host tiling 的开关在源码里完全正确，设备上执行的却是另一份实现，而「我改了」和「设备上跑的是我改的」之间，需要一条独立的证据链：一个探针，一个最小复现，或者一道让错误配置编译不过的检查。

量具也要和被测对象一样被怀疑。我们用逐 token 相等做了三个阶段的验收，直到最后才发现，在服务规模的并发下，去掉动态校验的参考实现自己就不可复现。归因的顺序应该是：先确认门槛本身可复现，再确认 lane 真的生效，最后才看输出。顺序反过来，就会把量具的问题当成功能的缺陷。

算子那边留下了一对接受变长输入的实现，和一组不调用任何 kernel 的独立参考。图那边留下了一套所有档位共用的状态契约。而门槛留下的东西更长久一些：在拿任何判据去判定别人之前，先让它判定一次自己。

`[8, 0, 0, 0, 0, 0, 0, 0]` 那一组的教训，其实不在变长算子里。一个本来用来识别异常的比较，因为两个数恰好相等而静默通过，于是后面所有的检查都建立在一个没有发生过的判断上。

下一次再遇到「改了却没有变化」，我们会先问：这次比较，是真的通过了，还是只是相等了。
