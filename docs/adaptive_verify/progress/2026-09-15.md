## 2. review 复核结论:昨日多处判断被撤回/降级

逐条 recheck 了代码/事实,**8 点基本全成立**,其中 1/3/5 直接推翻昨天的判断:

1. **[撤回] "confidence 尾部过自信"口径错误。** `av_observe` 的 `acc[i]` 是**前缀 survival**
   P(accepted≥i+1);而 confidence[i] 是**条件**每位概率(上游 `_assign_draft_token_budget`
   对它 `cumprod` 才成 survival)。我拿 raw conf vs acc 是**条件比边际**,必然越往后差越大——
   即便是完美标定的条件头也会被误判为"过自信"。正确口径:**逐样本 `cumprod(conf)` vs acc**
   (逐样本累乘再平均,不能对均值累乘)。粗算 `cumprod(conf)` 反而**偏低(欠自信)**。
2. **[成立] 观测未按请求/slot 对齐,且有 NaN 未上报。** 对齐靠"前若干行",churn 会系统性错配;
   bs16 日志有 2 行 `reqs=127 ... conf=nan gap=+nan`(prefill 突发),昨天没交代;shadow 也没
   finite 检查。
3. **[降级] cost-table smoke 通过 ≠ 曲线平坦可止损。** `monotonic=True` 是建表
   `np.maximum.accumulate` 造出来的(已核 `adaptive_verification.py:build_table`),不是稳定性
   证明;`set_initial_cost_curves` 已按 shape 取 `np.median`(所以"改 median-of-N"多余)。更关键:
   当前 profiling 用**临时 manager、未建真正 AV varlen 图**,dummy batch 可能跨 eager/uniform-FULL
   路径,`tok256≈89ms` vs 邻居 ~220ms 就是执行模式差异。**"低并发无价值"降级为待验证。**
4. **[成立] shadow 只是稳态近似**,不能宣称等价真实 manager,也不能当阶段闸门。已在实现与计划
   里明确标注为"受限模拟器"。
5. **[改] "mean accept length 一致"是错的验收。** 裁剪本就会降接受长度。拆成:正确性(greedy
   逐 token + 多轮 KV/SSM 态)/ 性能(允许接受长度降,比吞吐/TPOT/尾延)/ 采样语义。
6. **[采纳] GDN 阶段补跨轮用例 + 区分诊断入口 vs 正式 AV + TP 一致性提到首个 TP4 测试。**

### 5.2 NPU 冒烟 (a) 失败:装上 manager 即坏(cap=99 不裁也坏)

- **配置**:`ENABLE_DCUT=1`,`DCUT_MANUAL_CAP=99`(= 不裁,capacities=scheduled)。
- **表现**:拉服务 + 推理**全程不报错**;但增量输出**乱码**,**接受率恒为 0**(所有 draft 被拒)。

**诊断收敛**:cap=99 时 `compact_batch` 原样返回,`reallocate_drafts` 用 capacities(=scheduled)重算的
`cu_num_logits = cumsum(drafts+bonus)`、`query_start_loc = cumsum(drafts+non_draft)` 在**数值上与常规
非-AV 路径一致**。→ **坏的不是裁剪数学,而是"装上 manager 本身"改变了执行**。装上 manager(即使不裁)
相对常规路径只多改两件事:
1. **cudagraph 被强制 `FULL_AND_PIECEWISE`**(base:574,仅当 manager 非 None)。与之前"confidence 在
   FULL 图下冻结"是**同一类** FULL 图捕获问题;而步骤①/②是在**无 manager**(常规 DSpark 图)下过的,
   FULL_AND_PIECEWISE 下的 GDN spec 变长 decode 是**未验证过的捕获形状**。
2. **走 AV 的 `reallocate`/`compact` + fia padding 路径**(#15098 是围绕 fia/attention 后端设计的);
   若 GDN 的 metadata builder / 采样消费的 `query_start_loc`/`positions`/`ssm_state_indices` 与 AV 重建的
   布局错位,**接受率=0 正是 logit/token 布局对不上的典型症状**。

### 5.3 明日排查(按信息量排序)

1. **eager vs 图隔离(决定性)**:manager 开着 + 强制 eager/关 full cudagraph 再跑 cap=99。
   - eager 下**恢复正常** → 是 `FULL_AND_PIECEWISE` 捕获路径的锅(假设 1,同 confidence-frozen 类);
   - eager 下**仍乱码** → 是 `reallocate`/布局的锅(假设 2)。
2. **打印 `self.use_fia`**:决定 reallocate 走 fia(:447)还是非-fia(:442)分支;Qwen3.6-27B 有全注意力层,
   大概率 `use_fia=True`。
3. **布局 diff**:cap=99 时 dump AV 路径的 `num_scheduled_tokens`/`query_start_loc`/`cu_num_logits` 与
   无-manager 基线逐元素对比——**应当完全相同**,任何差异即 bug 点。
4. **GDN builder 口径**:确认 `gdn_attn_builder.py` 是读 AV 重建后的 `query_start_loc`/`positions`,
   还是自建;manager 若改了它消费的 seq_lens/positions,spec metadata(`ssm_state_indices`/
   `actual_seq_lengths`)就会基于错位计数构建。
