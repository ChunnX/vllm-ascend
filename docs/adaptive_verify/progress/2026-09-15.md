### 5.4 代码定位:捕获普通 decode,运行时却准备 spec metadata

**已确认的代码机制**:

1. 人工工厂绕过 GDN varlen/backend 与 `AttentionCGSupport.ALWAYS` 检查后创建 manager。
   D-Cut 算子支持变长,不等于 GDN 整个 forward 已具备变长 FULL 图能力。
2. v0.28.0 base 在 manager 非空时设置 `FULL_AND_PIECEWISE`,并将 `varlen_decode=True` 传给
   graph manager。因此初始配置日志中的 `FULL_DECODE_ONLY` 不能代表最终执行方式。
3. 变长图 descriptor 的请求数为 `min(num_tokens, max_num_seqs)`。8-token 图在本配置下按
   **8 个请求 × 每请求 1 token** 捕获;dummy query 边界为 `[0,1,2,3,4,5,6,7,8]`。
   GDN 捕获 builder 用 `diff(query_start_loc)-1` 得到全零 draft 数,Ascend builder 选择普通 decode。
4. 单请求完整验证为 **1 个请求 × 8 tokens**。FIA padding 后边界为
   `[0,8,8,8,8,8,8,8,8]`,实际 GDN metadata 按 spec decode 构造,但 FULL replay 不重新执行
   Python 分支选择,仍调用捕获的普通 decode 算子和其缓冲区引用。

这是一处具体的 capture/replay 分支契约缺陷,与用户提供的 8-token replay 和 eager 成功结果
吻合,是当前优先修复的根因。修复后的 FULL 回归尚未进行,暂不宣称已排除所有其他图问题;
也不再将其直接等同于此前 confidence-frozen 故障。
