## 2. 缺陷一:KV cache group 的 block table 被跨组共享(`e41230fc7`)

`2bb8a9c5c` 把两个 GDN 预处理修正接回 `build()` 时加了 batch 级记忆化——因为两个函数都会
重建 `query_start_loc`,而共享 plan 用张量地址认 batch。**问题是缓存的是整个 metadata 对象**,
而它携带 `block_table_tensor`。

`_shared_batch_plan_key` 自己的 docstring 就写着它"excludes `block_table_tensor` and
`slot_mapping`,the only two fields `build_attn_metadata` varies per group",而我的缓存键里
只有循环不变量的指针(各组同一对象),于是:

- 第 0 组算出 metadata 存进缓存
- 第 1..9 组命中缓存,拿到第 0 组的 `block_table_tensor`
- `build()` 用 `m.block_table_tensor` 推导本组 conv/recurrent 状态索引

Qwen3.6 的 Mamba 层分在 10 个 KV cache group 上,**9 组去别组的槽位读写 SSM/conv 状态**。
dcut 开关无关、图模式无关,eager 也一样错。

**修法**:缓存被修正的**字段**(两个 query 字段 + token 数 + `is_prefilling`,都是
`build_attn_metadata` 的循环不变量),再 `replace` 回每组自己的 metadata。字段值是同一批张量
对象,所以下面的 plan 仍然只算一次,而 `block_table_tensor` / `slot_mapping` 保持各组自己的。

**配套测试也是错的**:原测试断言两组拿到 `is view`(同一对象)——把缺陷写成了要求,而且给两组
传了同一个 metadata 实例,根本看不出差别。已改成构造两组不同 block table,断言"一次修正、
两张 block table"。

## 3. 缺陷二:开启 AV 会改掉编图几何(`0d6dd7559`)

`vllm/v1/worker/gpu/model_runner.py:591` 用 `varlen_decode = self.adaptive_verification is not None`,
所以**开 D-Cut 就把 decode descriptor 从 uniform 切成 varlen**:

| | 描述符行数 | bucket q=8 的 dummy | capture 的 accepted/draft |
| --- | --- | --- | --- |
| `varlen_decode=False`(dcut=0) | `q // (K+1)` | **1 行 x 8 token** | `[8]` / `[7]` |
| `varlen_decode=True`(dcut=1) | `min(q, B_max)` | **8 行 x 1 token** | `[1]*8` / `[0]*8` |

真实 spec batch 回放的是 `N 行 x (K+1)`。匹配条件 `min(Q, B_max) == Q/(K+1)` 只有
`Q = B_max*(K+1)` 一个解,所以除了恰好满并发,**每个 bucket 的几何都是错的**。
`max_num_seqs=1` 正确是因为 varlen 在那里退化成了 uniform 几何,不是并发低。

full attention 能容忍这种差异——它每步用 `graph_task_update` 以刷新后的主机侧长度重发
kernel;**linear_attn 没有任何 replay 期刷新**。`attention_v1.py:802` 的注释说这些层"由
`update_conv1d_graph_params` 单独更新",但**该函数在全仓不存在**,只出现在这条注释里。
过滤是真的,承诺的另一条路径是空的。

**修法**:D-Cut 路径保留 uniform 描述符,即不带 D-Cut 时已验证通过的那批图。裁剪后的 batch
不是 uniform,匹配不到 FULL descriptor 而回落,比回放一张为别的布局编的图要好。可用
`VLLM_ASCEND_DSPARK_DCUT_UNIFORM_DECODE_GRAPH=0` 恢复旧行为做对照。
