## 2. 问题一:`[8,0,0,...]` 重编译后还是 fail

D-Cut Conv1D 的 host tiling 会忽略 `query_start_loc`:2D + runMode=1 默认按"每 request
一个 token"读形状,只有 token 数与 request 数不等时才走变长读法。`[8,0,...]` 恰好 8 token /
8 request,于是第 0 行只拿到 `{start=0,len=1}`,token 1..7 落到空行上被整段跳过。

加了 `CAUSAL_CONV1D_QUERY_START_LOC_DEFINES_LAYOUT` 宏、只在 D-Cut 编译单元置 1 —— **重编
之后还是 fail**。我先以为是没装上,查完 `.so` 时间戳确认装上了。

真因是链接:三个共享 tiling 头把 helper(包括被这个宏改动的 `GetShapeDtypeInfo`)全放在
`namespace optiling::causal_conv1d_host` 里且全是 `inline`,而 `#define CausalConv1d
DcutCausalConv1d` 只改算子名那一个 token,**命名空间和函数名都没改**。两个编译单元发出同一
个 mangled symbol 而函数体不同,`inline` 的 vague linkage 让链接器只留一份并静默丢掉另一
份,留下的通常是宏=0 的 stock 那份。

**修法**:D-Cut 编译单元再 `#define causal_conv1d_host dcut_causal_conv1d_host` 隔开符号,
并在头里加 `#error`——开了 layout 策略却没隔离命名空间直接编译失败。**为什么这么修**:
问题不在语义而在符号唯一性,只改宏永远不会生效;`#error` 是为了下次不会再静默退回旧行为。

本地用两个 TU 复现过:`-O0` 拿到错值,`-O2` 因为内联反而看不见——这也解释了为什么它能藏这么久。

## 3. 问题二:「相等」根本不是证据(今天最大的收获)

整网脚本一开始的判据是"逐 token 与 baseline 相等"。踩了三层:

1. **只有横幅没有数据行**:第一次跑 interval=50 而整个生成只有约 20 步,聚合行一条没打,
   我却把启动横幅当成了证据。横幅只证明 manager 被构造,不证明它决策过预算。
   → logger 改成第一条记录到的步数**一定**打印,脚本要求日志里出现 ` steps | `。
2. **`kept=100%` 的相等等于没验**:没裁剪过的 lane 校验宽度和 baseline 一样,相等什么都
   没说明。→ 非 `threshold:0.0` 的 lane 若全程 `kept=100%` 报 `INCONCLUSIVE` 并返回非零。
3. **baseline 自己在 bs≥16 不可复现**。这一条推翻了我今天三个"mismatch=缺陷"的结论:
   把 baseline 跑两遍(`baseline2`)对比,**它和自己就不相等**。原因是 batch 组成变化 →
   kernel tiling / reduce 顺序变化 → 舍入变化 → greedy argmax 翻转。

**修法**:每次都跑 `baseline2` 当噪声底,lane 只在"差异数 > 底 或 首个分歧位置 < 底"时判失败。
**为什么这么改**:token 相等只在参考自身可复现的并发上有效。所以**正确性结论的范围明确限定
在 bs=4**(噪声底为 0),高并发改用接受率作为仪器——但要记住 per-position 接受率是除以
`num_drafts` 的,裁剪会按构造压低后面几位,不能直接当退化。

旁证:你自己 `vllm serve` 16 并发、THRESHOLD=0.4 没有乱码,这独立地反对"结构性状态损坏"。

## 4. 问题三:上游 vLLM 的一个真 bug(已整理成 issue)

开 prefix cache + 异步调度后报 `DSpark confidence contains non-finite values`。查下去发现
上游 `AdaptiveVerificationManager` 对 confidence **完全不做校验**,而一个 NaN 行会:
`np.sort` 把 NaN 排最后 → `[::-1]` 翻到最前 → `cumsum` 全 NaN → `argmax` 返回第一个 NaN 的
下标。**一个请求的坏行,整批 `draft_budget` 从 7 塌到 1**,不报错不打日志。

纯 NumPy 可复现(见 issue 草稿)。**修法**:我们这侧改成**按行不信任**而不是抛异常——坏行保留
自己的 draft,并计入 `untrusted_rows` 打出来。**为什么**:1.0 本来就是 manager 对"没有信息的
槽位"的取值,不需要新约定,而且方向保守;抛异常会让一个局部坏行杀掉整个请求。

## 5. 问题四:阶段 B 的清单,我自己写错了两项

清单列了六项前置。逐项对代码核完之后:

- **第 2 项(`B_fia` 请求轴)已经在树上**——就是 `_pad_adaptive_query_start_loc_for_fia()`,
  把裁剪后的 `query_start_loc` 补到 `batch_desc.num_reqs`,padding token 在 padding 请求之间
  **均分**,正是文章 §3.4.3/3.4.4 的写法。
- **第 4 项(padding 生命周期)已经在树上**——`seq_lens_np[num_reqs_padded:] = 0`。
- **第 1 项不需要新代码**。varlen 捕获出来的描述符是 `num_reqs=min(Q,B_max)`、
  `max_query_len=K+1`,注释原文"any mix of 1..decode_query_len tokens per request",而
  `_is_compatible` 只要求请求不多、token 不多、query 不长——**裁剪批天然满足**。把它关掉的是
  阶段 A 自己加的那句 `varlen_decode = False`。

所以阶段 B = **不再执行那一句 + 固定 GDN 轴**,两半是一件事:隔壁分支 `0d6dd7559` 关掉 varlen
捕获的原因就是状态算子的几何错配,而文章对它的答案正是固定轴。**为什么把轴做成模式的一部分
而不是第二个开关**:ragged + 按桶轴是已知会坏的那个组合,不应该可达。

## 6. 阶段 B 为什么值得做(A′ 的实测)

阶段 A 的实测修正了一个说法:裁剪批**不是**回落到 eager,而是回落到 **PIECEWISE**(上游在 AV
生效时把模式设为 `FULL_AND_PIECEWISE`)。所以问题不是"能不能入图",而是"ragged FULL 比现在
这套 FULL+PIECEWISE 还能多拿多少"。只有真实 cost table 能回答:

| 并发 | cost table 跨度 | 说明 |
| --- | --- | --- |
| bs=4 | 0.00ms(Q=8..32 全是 116.80) | 全部落在 FULL 内,曲线是平的 |
| bs=16 | 144.26ms | 有梯度 |
| bs=32 | 263.00ms | `Q=64:136.84 → Q=72:218.34`,8 个 token 差 81ms |

**bs=4 上没有收益不是结论**,那里曲线本来就平。服务规模下曲线有梯度,这是阶段 B 的实测依据,
而不是"文章说要做"。
