## 3. 仪表自己踩的坑

仪表在一个本来就在失败的运行上,不该再成为失败源。今天它把运行挂了三次:

1. `getattr(_EXTRA_CTX, 'capturing', False)` —— `getattr` 的默认值只吞 `AttributeError`,
   forward context 未设置时抛的是 `AssertionError`。
2. `self.layer_names` 不存在 —— GDN 基类 `__init__` 不调用
   `AttentionMetadataBuilder.__init__`,而那是唯一设置该字段的地方。
3. (上线前拦住)`enabled()` 在 guard 之外运行,TP 组未起时 `get_tensor_model_parallel_rank()`
   会抛。

三次都发生在**调用点组装字段时**,不是在 helper 内部。改法:`guarded()` 上下文管理器包住三个
调用点,首次异常打一次带 traceback 的告警并把该组件停用,其他组件继续;`enabled()` 自己
try/except 且不缓存未决结果。另外把日志收到 TP rank 0(`d77dcfde3`),4 卡日志才读得动。

去重键也修了两次。原来的键只有"请求数 + token 数",而 eager warmup 会先构造出和图步完全
相同的计数,把额度吃光——**结果 FULL 那一步一行都不打,看起来像 builder 根本没被调到**。
`90862091c` 给三个键各加判别位(图模式 / GDN 分支计数 / 首行 query 长度),`f35404502` 再给
FIA 加首行 KV 长度(capture 带 dummy KV 长度,replay 带真实长度,正是要对照的那一对)。

## 4. 排除过的假设:方法、动机、结果

方法上只认两种证据:代码路径,或实测日志。凡是"推断"的一律标为未验证。

| 假设 | 为什么查 | 结果 |
| --- | --- | --- |
| CPU 镜像取错(`seq_lens_np` padding 行不刷新) | `prepare_attn` 只转发 `seq_lens_np`,不转发新置零的 upper bound | **排除**。实测 `pad_seq_lens_np` 与 `pad_upper_bound` 全零且一致 |
| capture/replay 分支不一致 | 修前 capture 进 spec、replay 可能落 decode | **已修并复验**。两边都是 `spec=1 decode=0 prefill=0` |
| GDN metadata 形状/地址不匹配 | 图固定地址,GDN 层没有 replay 期参数更新 | **排除**。`spec_qsl` / `num_accepted` / `state_indices` / `masks` / `spec_token_indx` 五项的形状与指针逐字段相同 |
| FIA sink 保留了捕获期 block table | 代码里确有这条分支 | **排除**。`has_sinks` 只由 v1 runner 传入,MRV2 下该分支永不进入 |
| `B_gdn` 跟随 token bucket | 上游同类实现放弃过这个设计,症状一致 | **确认存在**(`b_graph=8` vs `b_max=32`),但它在同一个 bucket 内 capture/replay 一致,**不解释本故障** |
| capture/replay 几何不同(8×1 vs 1×8) | varlen dummy 把 token 按 1/请求均摊,只有满并发那个 bucket 的几何与 replay 一致 | **推翻**。`max_num_seqs=1` 下两边都是 1 行 × 8 token、地址全同,仍然全 0 |

最后一条是我今天最大的一次判断失误:我据排除法把它顶成唯一候选,还推导出"只有满并发能对"
的预测。外部 review 早先就指出过 kernel 在运行时读长度、`MAX_MTP` 是编译期常量,我当时接受
并降级为未验证假设,后来又因为排除法把它重新升格。`max_num_seqs=1` 这一把直接证伪。

**留下的正面价值**:`min(q, B_max) == q/(K+1)` 只有 `q = B_max·(K+1)` 一个解,所以在当前
varlen 编图口径下,"低并发的图几何按构造就和 replay 不同",这仍然是要修的(F1′),只是它不是
今天这个故障的原因。

## 5. 两个新的代码发现

1. **`update_conv1d_graph_params` 不存在。** `attention_v1.py:802` 的注释说 linear/GDN 层
   "由 `update_conv1d_graph_params` 单独更新,所以这里用 `seq_lens_list` 非空过滤掉它们"。
   全仓搜索,这个函数只出现在这条注释里。过滤是真的,承诺的另一条路径是空的——**GDN 算子在
   replay 期没有任何主机侧刷新机制**。这本身未必是缺陷(输入若全是固定地址的设备张量,捕获的
   task 每次 replay 会重读设备内存,而地址我们刚验证过都对),但该事实要写进设计文档 §1.6,
   不能再靠这条注释安心。
2. **开 D-Cut 会在图里换掉两个算子。** `gdn.py:329` conv 从
   `npu_causal_conv1d_custom(run_mode=1)` 换成 `npu_dcut_causal_conv1d`;`gdn.py:490`
   recurrent 从 `npu_recurrent_gated_delta_rule` 换成
   `npu_dcut_recurrent_gated_delta_rule`。而 `gdn.py:301` 的注释自己写明了不变量:step 1
   保留完整校验长度、不裁剪,**所以必须与定长路径逐位一致**。cap=99 下 metadata、几何、地址
   都已证实与 dcut=0 无差别,剩下的唯一差别就是调了哪个 kernel。
