## 2. FIA padding 行:一次三连错

设备报 `16 vs 17`,`max_num_seqs=16`。根因是缓冲宽度不对称:`query_start_loc` 是
`max_num_reqs + 2`(注释直接指向 FIA padding),其余每请求缓冲只有 `max_num_reqs`。

**第一次错:方向反了。** 我加宽了缓冲让那个批活下来。而文章 §4.5 写着:

> 含真实 prefill 或不满足契约的 mixed batch:退出 ragged FULL……**不能为了命中图,强行把
> 一个不符合捕获契约的 batch 塞进去。**

两次崩溃的批都是 **15 decode + 1 prefill**。正确的做法是把它挡在外面,不是让它活下来。

**第二次错:清零引发回归。** 为了让 padding 行"惰性",我把它们的 `seq_lens` 清零。
这让 `_remove_spec_graph_padding_queries` **第一次真正执行**(此前 padding 行带残留长度,
`inactive` 恒假,函数一直提前返回),而它是**截掉**那些行 —— GDN 请求轴于是从 B_max 变成
跟着活跃数走。文章 §4.4 记的正是这个故障:

> 不同 Q 使用了不同的 GDN 请求轴和 tiling……把所有 bucket 的 GDN 轴固定为 B_max,并让空行
> 成为确定性的零长度状态后,问题得到解决。

文章要求**保留空行**,代码是**截掉空行**,两者不兼容。已撤销。

**第三次错:归因错了又自己推翻。** 我先说"早先没开 FIA sink 所以没撞上"——`use_fia` 查的是
**目标模型**有没有层用 `AscendAttentionBackend`,显式排除 draft 层;而 `fia_sink_selected`
认的是 draft 判别位。两者名字撞了、含义无关,环境变量根本不影响 `use_fia`。

真实原因是 padding **请求**和 padding **token** 是两回事:槽位满了只消掉前者,后者来自裁剪。
bs=4 那轮多数步只有 3 个活跃请求,有 padding 请求可用,走"均分"分支不会加行——**短跑侥幸
躲过,长跑必然撞上**。

## 3. 读错了版本的 vLLM

一天内两次因为抄错签名让设备白跑,根因同一个:

```txt
本地 checkout: v0.28.1rc0-679-gce08bb5b34
部署钉死:      v0.28.0                      ← 差 679 个提交
```

`CudaGraphManager.dispatch` 在本地有 `num_ubatches`,0.28.0 **没有**。第一次是覆写方法时
顺手重写了构造调用(`model_runner` 是第 5 个位置参数,我把 `lora_capture_cases` 塞了进去);
第二次是包装 `dispatch` 时按本地签名传了 6 个位置参数。

**规矩:`git show v0.28.0:<path>`,不读工作区。** 更好的是不抄——拒绝逻辑最终放在
`_dispatch_pcp_and_sync_dp`(本仓库自己的拦截函数),`*args, **kwargs` 原样透传,
要改的两个字段用 `dataclasses.replace` 按名字改。**既不复述签名也不复述字段表。**

顺带发现 0.28.0 本来就想挡这件事:`BatchExecutionDescriptor.max_query_len` 的注释写着
"this is what keeps a prefill batch out of one"。但 **prefill 比 decode 宽度还短时会漏**——
两次失败的 prefill 是 6 和 7 个 token,decode 是 8。我们的判断是补这个漏洞,不是另起一套。

## 4. 只做了文章的一半

拒绝混合批之后吞吐从约 500 掉到 457。文章的原文是「退出 ragged FULL,**按场景使用 eager
或原生安全组合路径**」——我实现了 eager,没实现后半句,而且另一个改动(把
`FULL_AND_PIECEWISE` 降级)把那条路堵死了。**单看每一个改动都站得住,合起来才出问题。**

但随后对方指出:**关 AV 时混合批也是落 eager 的**,让开 AV 独享 piecewise 会把收益测高。
而且**崩溃那版配的同样是 `FULL_DECODE_ONLY`,piecewise 从头到尾没参与**——那 9% 是混合批
从(错误进入的)ragged FULL 掉到 eager,不是 piecewise 掉到 eager。我的整个框架是编的。

**项目决定:不用 piecewise**(多一族图,显存吃不消)。所以配置定死 `FULL_DECODE_ONLY`、
混合批落 eager、两边一致,那 9% 在此前提下无法靠配置回收。

文章列为**将来方向**的那条(把 prefill 和 decode 拆成独立 microbatch)措辞是「后续若要」——
**参考实现自己也没做**,所以那不是抄作业。

## 5. 两个脚本一直在悄悄漂

门槛脚本又崩在 `too many values to unpack`——**编译缓存的修复我只做在吞吐脚本里,没搬过来**。
`--cudagraph-mode` 也是同样的情况。两个脚本各自建引擎,一边的对齐另一边不生效。

补了一个 CPU 检查:解析两个脚本的 `child_env`,把"被显式清掉的 key"识别为 lane 开关排除,
**其余都算引擎配置,必须一致**。用变异验证过它会响。

写这个检查时抓到第三处漂移:`VLLM_ADAPTIVE_VERIFICATION_PROFILE_CONTEXT_LEN` 吞吐脚本
**根本没设**,按上游默认 8192 做 cost table profiling,而实际只跑 4096。

**但这一条我当时判断错了,而且错在同一个形状上:我没去读它生效的地方。**
`set_dummy_context`(`vllm/v1/worker/gpu/input_batch.py:223`)第一步就
`min(context_len, max_model_len - query_len)`,所以请求值只在 `max_model_len` 以下生效。
两个脚本的 `max_model_len` 都低于 8192,profiling context 一直就等于它——**这个"修复"在
当前配置下是 no-op**,+3.6% 那组数不受影响,不需要因此重测。保留它只是为了与上游文档的
用法一致,并在 `max_model_len > 8192` 时才真正起作用(那时偏差方向反过来)。

漂移检查本身的价值不变:它抓到的是"两个脚本的引擎配置不一致",这点是真的。错的是我给
这处不一致编的后果。

## 6. 今天的教训

三次错误是同一个形状:**在一个地方验证/修复,然后假定它在别处也成立**。

- 抄签名:假定本地 checkout 等于部署版本
- 照文章做:假定取其中一条路径等于实现了那一节
- 修脚本:假定修好一个脚本等于修好这类问题

对应的三道护栏都已落地且验证过会响:pinned tag 读源码(写进文档)、不复述外部签名和字段表
(结构上做到)、两脚本引擎配置一致性检查(CPU 用例 + 变异验证)。

还有一条流程教训:我用 `pytest | tail -2` 把退出码吞了,**带着两个失败的测试提交过一次**。
以后这类检查不走管道。
