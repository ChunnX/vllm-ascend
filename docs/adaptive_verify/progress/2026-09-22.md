## 2. 阶段 B 成立:裁剪批真的进了全图

判据是 **`graph=FULL` 与 `kept<100%` 同窗出现** —— uniform 模式下不可能(裁剪批必落
PIECEWISE)。两次都拿到了,而且噪声底 identical:

```txt
5 steps | ... | kept=73.1% | trimmed_steps=4/5 | conf_moved=5/5 | graph=FULL=5
```

第二次把轴放宽到 16、并发压在 4,制造 **13 行 padding**,专门压固定 GDN 轴——那正是隔壁分支
`0d6dd7559` 当初坏掉的地方。也 MATCH。

**真正的回报在 cost table 里。** 同为 bs=4:

| | 阶段 A(uniform) | 阶段 B(ragged) |
| --- | --- | --- |
| Q=8..32 | 116.80 全平 | 33.37 → 42.13 **单调** |
| 可达 spread | **0.00ms** | **12.31ms** |
| controller 决策 | `kept=100%`(不裁) | 16/20 窗口裁 |

因果链闭合:曲线平 → argmax 永远选最大 Q → 裁剪买不到东西;有梯度 → 才开始裁。阶段 A 的
`kept=100%` 不是缺陷,是对一张平表的正确决策。

## 3. 从「实验通了」到「功能通了」

查激活路径发现:**不设环境变量的话整套适配是关的**,`enable_adaptive_verification: true`
单独开拿到的是上游未改的 manager。所有验证都靠三个环境变量撑着。

现在一个配置项决定全部。两个设计决定:

- **图模式默认值按 lane 分,不是全局的。** lane A 每步算精确 host 容量,是捕获的图付不起的;
  全局默认 ragged 会把二分工具塞进它跑不了的图里。
- **配置不支持时退回上游 manager 并打 warning,不是起不来。** 那是这条路径成为默认之前
  PP≠1 / LoRA / DBO 本来会得到的行为。显式点名 lane 才报错——默认不该把原本能跑的配置打挂。

## 4. −11% 的回归是我们自己的实现

specbench 上打开 AV 曾经 TPOT 18.10 vs 16.30ms。少收 2% 的 token 却多花 11% 的时间,说明
多出来的时间不在校验宽度上。

根因:`record_confidences` 做 `current.cpu().numpy()`,**阻塞等这一步 drafter 刚产出的
confidence**。上游是双缓冲 + side stream + event,只等两步以前早已落地的拷贝。同步版每步
把 host 和 device 串成一条,异步调度完全不重叠。

改法:按上游建 side stream,建不出来退回阻塞拷贝并打 warning(设备上确认建成了)。NaN 修复
挪到**设备侧** `torch.nan_to_num`——它从来不需要 host 上的值,在 host 上修才是那次阻塞拷贝
的唯一理由。两个探针改成**设备侧累加、每窗口读一次**:为了测量这个停顿而每步付一次拷贝就
荒谬了。

之后 18.10 → **16.09ms**。

另外发现一个上游**不付**的每步开销也是我加的:`get_tp_group().broadcast()` 每步一次。上游
只在 cost curve 初始化时 broadcast 一次。TP=4 下那是每个 decode 步一个同步集合通信,已改成
默认关(`VLLM_ASCEND_DSPARK_AV_TP_BROADCAST=1` 可恢复)。

## 5. 收益:还没测出来,这和「没有收益」不是一回事

修完之后 specbench 三组:16.086(ragged)/ 16.130(ragged+piecewise)/ 16.299(关闭)。
**1.3% 不能叫收益**,两个独立理由:

- **三次跑的活儿不一样。** 关 AV 多生成 6.5% 的 token、输出长 7%,而 TPOT 随上下文增长。
  挑出长度差 2% 以内的类目:extraction AV **差 11.5%**、math 好 3.0%、roleplay 好 2.8%。
- **数据自带噪声估计。** 两次 AV 跑配置差别很小,却在 math 上差 **5.9%**。类目级噪声几个
  百分点,1.3% 落在里面。

**bs=4 的天花板本来就只有约 17%**:整步 ≈ TPOT × AvgSpecLen ≈ 70ms,verify 占约 60%,其中
只有 spread 12.31ms(42ms 的 29%)随 Q 变化。实测 AvgSpecLen 只从 4.33 降到 4.27。所以
约 1% 在预期量级内,不是缺陷。

## 6. 测试方法对齐 15098 / 15147

写了新脚本 `examples/dspark_adaptive_verify_throughput.py`。过程中撞掉自己四个错误:

| 我原来的做法 | 为什么错 |
| --- | --- |
| 扫 K = 5/7/9 | `speculative.py:177` 要求 `num_speculative_tokens` **精确等于** checkpoint 的 `block_size`。block7 上 K=5/9 连引擎都起不来。15098 那三行是**三个 checkpoint**。 |
| `--concurrency` 既当并发又当请求总数 | 15147 是「并发 64、**500 请求**」。只发和批一样宽的请求数是在测**一波**,不是持续吞吐。 |
| 扫 `max_num_seqs` 当作扫负载 | 它同时决定捕获 bucket 集合、`graph_limit`、cost table 可达范围、固定 GDN 轴宽度。实测 `graph_limit` 在 4 是 32、在 16 是 **128**——两格是**两种图配置**,差异归因不了。现在默认只跑部署点 16。 |
| Dolly 只取 `instruction`;取前 N 条 | 丢掉 `context` 会让 closed_qa/summarization 失去意义;500 条从 15011 条取头部很可能整段同类目,而**类目决定接受率、接受率决定结论**。现改为拼接 + 等距取样。 |

15147 还回答了 15098 没说的数据集问题:Math500 **+8.5%**、Dolly **+19.1%**,并发 **64**。
两者的顺序就是接受率——数学的 draft 接受得好,可裁的更少。**所以 MATH-500 是对 AV 最不利
的数据集**,而我们第一次恰好挑了它。

上游 vLLM 那边(47808)`tests/v1/spec_decode/test_adaptive_verification.py` **全是 CPU
单测**,没有吞吐用例——性能数字只出现在 PR 描述里。我们的分工形状是对的。

## 7. 今天的勘误

**「PIECEWISE 下 GDN 在图外 eager 跑」只在真配了切图时成立。** `splitting_ops` 在**配置时**
按配置的 `cudagraph_mode` 决定,而 AV 把模式改成 `FULL_AND_PIECEWISE` 发生在 model runner

"PIECEWISE"是**没切过的整模型图**,`enable_npugraph_ex` 也相同。此前怀疑的编译配置污染
**不存在**。

自己在 `resolve_cudagraph_mode_and_sizes` 里的同一个谓词。
